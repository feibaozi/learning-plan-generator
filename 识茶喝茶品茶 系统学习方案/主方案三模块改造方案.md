## 1. 总体改造概述

### 1.1 三模块新三角定位

```
              ┌─────────────────┐
              │   📐 方法论      │
              │  学习策略层      │
              │  "怎么学最有效"  │
              └────────┬────────┘
                       │ 指导
          ┌────────────┼────────────┐
          ▼            ▼            ▼
┌─────────────────┐  ┌─────────────────┐
│  🧠 知识图谱     │  │  🎨 图表指南     │
│  空间地图层      │  │  成果展示层      │
│  "知识间怎么连"  │  │  "我能画出什么"  │
└─────────────────┘  └─────────────────┘
```

### 1.2 改造原则

| 原则 | 说明 |
|------|------|
| **数据驱动** | 所有动态内容从 JS 数据生成，不硬编码 HTML |
| **纹理感知** | 方法论和图表指南根据 G1-G8 纹理自适应 |
| **状态持久** | 交互状态（完成/展开/筛选）存入 localStorage |
| **最小侵入** | 尽量不改变现有占位符体系，新增数据通过新占位符或 JS 计算 |
| **向后兼容** | 旧方案打开后三个模块降级为静态展示，不报错 |

## 2. 模块 1：知识图谱 → 交互式导航仪表盘

### 2.1 目标效果

| 维度 | 当前 | 改造后 |
|------|------|--------|
| 渲染引擎 | Canvas 2D API | ECharts 5.x（与深度资料统一） |
| 节点布局 | hash 伪随机 | 二维语义布局：X=阶段时间线，Y=主题层级 |
| 节点外观 | 4px 实心圆，按阶段着色 | 圆形节点 + KP 名称标签，按阶段着色；已研读=实心高亮，未研读=半透明 |
| 节点交互 | 无 | hover→tooltip（名称+一句话总结），click→跳转 KP 卡片并展开 |
| 连线 | 全部相同虚线 | 三档：前置依赖（实线粗弧线）、同级关联（虚线细）、跨阶段（浅色弧线） |
| 连线交互 | 无 | hover→高亮两端节点 + 显示关系类型标签 |
| 阶段区域 | 半透明矩形 | 渐变底色柱 + 阶段标题标签，hover→高亮该阶段所有节点 |
| 响应式 | resize 重绘 | ECharts 内置 resize + window 监听 |
| 状态同步 | 无 | syncKPsFromManifest() 触发后自动刷新节点颜色 |

  进阶   │                    ● 风土         ● 收藏
  ──────┼────────────────────────────────────────→

### 2.3 数据模型设计

#### 2.3.1 新增全局数据 `GRAPH_DATA`

在模板 `<script>` 的数据段新增，通过 `%GRAPH_DATA%` 占位符注入：

```javascript
var GRAPH_DATA = {
  nodes: [
    {id:'p1_1', x:0, y:0, label:'茶树品种与起源'},
    {id:'p1_2', x:0, y:1, label:'六大茶类分类体系'},
    // ... 共 KP_COUNT 个
  ],
  edges: [
    {from:'p1_1', to:'p1_2', type:'prerequisite'},
    {from:'p1_2', to:'p1_3', type:'related'},
    {from:'p1_2', to:'p2_3', type:'cross_phase'},
    // ...
  ]
};
```

#### 2.3.2 坐标计算规则（生成时由 Agent 计算，不依赖运行时 JS）

| 维度 | 计算方法 | 值域 |
|------|----------|------|
| `x` | `phase_index`（阶段在 PHASES 数组中的索引 0..N-1） | 0..PHASE_COUNT-1 |
| `y` | 根据 KP 的 `tag` 字段：`foundation`→0, `core_toolkit`→1, `integration`/`advance_frontier`→2 | 0..2 |

#### 2.3.3 边类型定义

| type | 含义 | 视觉 | 确定规则 |
|------|------|------|----------|
| `prerequisite` | 前置依赖 | 实线弧线 #6366f1 1.5px | 从 `next_kps` 推断 |
| `related` | 同级关联 | 虚线 #6366f144 1px | 从 `rel` 推断 |
| `cross_phase` | 跨阶段桥梁 | 浅弧线 rgba(99,102,241,0.2) 0.8px | rel 中 `p` 不同的关联 |

### 2.6 JS 变更逻辑

**替换 `drawGraph()` → 新增 `initGraph()`**:

```
initGraph():
  1. 检查 #graphContainer 是否存在，不存在 return
  2. 检查 typeof echarts !== 'undefined'
  3. 从 GRAPH_DATA 构建 ECharts graph series option
     - nodes: 遍历 GRAPH_DATA.nodes，查找对应 KPS
       · symbolSize: 12
       · color: PHASES[phase_index].color
       · opacity: 从 deep_dive.status 判断 (ready→1, none→0.4)
       · label: {show:true, formatter:KP.n}
       · tooltip: KP.n + KP.s
     - links: 遍历 GRAPH_DATA.edges
       · lineStyle 根据 type 区分
  4. 初始化 ECharts 实例，setOption
  5. 注册 click 事件：节点点击 → tKC_go(kpId)
  6. 注册 resize 监听
  7. 暴露方法 graphRefresh() 供 syncKPsFromManifest 调用
```

**修改 `syncKPsFromManifest()`**:
```
在更新 KPS 状态后，调用 graphRefresh() 刷新节点颜色
```

### 2.7 生成工作流变更（SKILL.md Phase 4）

Agent 在生成 HTML 时新增计算步骤：

```
Step 4.X: 构建 GRAPH_DATA
  1. 遍历 KPS，为每个 KP 分配 (x, y):
     x = PHASES.findIndex(p => p.id === KP.p)
     y = KP.tag === 'foundation' ? 0 : KP.tag === 'core_toolkit' ? 1 : 2
  2. 遍历 KPS，从 rel 和 next_kps 构建 edges:
     - 如果 KP_A.rel 包含 KP_B.id 且同阶段 → type='related'
     - 如果 KP_A.rel 包含 KP_B.id 且跨阶段 → type='cross_phase'
     - 如果 KP_B 在 KP_A.next_kps 中 → type='prerequisite'
  3. 序列化为 JSON 注入 %GRAPH_DATA% 占位符
```

### 2.8 依赖要求

- **ECharts CDN**：当前 base_plan.html 不引入 ECharts，需要判断是否引入。
  - **方案**：知识图谱模块始终使用 ECharts，在模板 `<head>` 中始终加载 ECharts CDN（与深度资料统一，`echarts@5.5.0`）。这带来额外 ~1MB 加载，但知识图谱功能对用户体验提升显著。
  - **替代方案**：保持 Canvas 但增加交互。不推荐，工作量更大且效果不如 ECharts。

### 3.6 JS 变更

**新增 `hMS()` + `tMS()`**:

```
hMS():
  1. 检查 #methodSteps 是否存在
  2. 从 localStorage 读取已完成步骤 ID 列表
  3. 遍历 METHOD_STEPS 渲染步骤卡片
  4. 每个卡片：
     - 如已完成，加 .done class
     - 如有关联板块，渲染跳转链接（onclick → scroll + highlight）
     - 如有示例，渲染 mini 预览
  5. 更新进度计数

tMS(stepNum):
  1. 读取 localStorage 中已完成列表
  2. toggle 该步骤
  3. 重新渲染步骤卡片样式（加/去 .done）
  4. 更新进度计数
  5. 更新全局进度条（uPB）
```

**修改 `init()`**:
```
原: %METHOD_STEPS_HTML% 直接注入 HTML
新: 调用 hMS() 动态渲染
```

**修改 `uPB()`**:
```
将方法论完成度纳入进度计算：
  progress = (tracker_done + method_done) / (tracker_total + method_total)
  或保持独立进度条（推荐，避免混淆概念）
```

### 3.7 生成工作流变更

```
Step 4.X: 构建 METHOD_STEPS
  1. 根据 texture 从纹理-方法论映射表选择模板
  2. 根据主题领域填充具体的步骤描述
  3. 如果有关联板块（如 G6 步骤1 关联 graph），设置 link_section
  4. 如果有示例图（G2/G6），生成 mini SVG 示例
  5. 序列化为 JSON 注入 %METHOD_STEPS% 占位符
  6. 删除旧的 %METHOD_STEPS_HTML% 占位符（模板中不再使用）
```

### 4.5 JS 变更

**重写 `hDS()` → 新增 `renderGallery()` + `filterGallery()` + `openLightbox()` + `closeLightbox()`**:

```
renderGallery(filterType):
  1. 收集所有 PHASES[].drawings[]（扁平化）
  2. 如果 filterType !== 'all'，按 type 筛选
  3. 为每个 drawing 渲染卡片：
     - 缩放 SVG 预览（在 .drawing-preview 内）
     - 类型标签（colored badge）
     - 阶段来源
     - 如果 related_kp 且 deep_dive.status==='ready'，渲染"📖 查看详细"链接
     - onclick → openLightbox(drawing)
  4. 更新筛选按钮的 .active 状态

openLightbox(drawing):
  1. 将 drawing.svg 完整注入 #lightboxImage
  2. 将 drawing 元信息注入 #lightboxInfo
  3. 显示 lightbox

closeLightbox():
  1. 隐藏 lightbox

filterGallery(type):
  1. renderGallery(type)
```

**修改 `init()`**:
```

新: renderGallery('all') → 渲染画廊
```

### 4.6 ASCII → SVG 转换方案

**方案：生成时转换（推荐）**

在 Agent 生成 HTML 的阶段，从 Markdown 方案中提取 ASCII 图，按以下规则转为 SVG：

| ASCII 元素 | SVG 转换 |
|------------|----------|
| `┌─┐└─┘├─┤│` 框线字符 | `<rect>` + `<line>` 路径 |
| `●○` 圆点 | `<circle>` |
| `→←↑↓` 箭头 | `<path>` 带 marker-end |
| 颜色标注文本 | `<text>` 带 fill |
| `────` 虚线/实线 | `<line>` 带 stroke-dasharray |

**替代方案：运行时转换**
在 JS 中用正则解析 ASCII 图生成 SVG。优点是不增加生成负担，缺点是运行时性能损耗且正则匹配不鲁棒。不推荐。

### 4.7 生成工作流变更

```
Step 4.X: 构建 DRAWINGS（替代原来的 PHASES[].drawings 字符串数组）
  1. 从 Markdown 方案中提取所有 ASCII 图
  2. 将每个 ASCII 图转换为内联 SVG（不超过 ~2KB 每个）
  3. 按阶段分组挂到 PHASES[].drawings
  4. 分配 type（通过关键字匹配：光谱/矩阵/流程/关系/时间线）
  5. 关联 KP（通过图表名称与 KP 名称的语义匹配）
  6. 序列化为 JSON 注入 PHASES_JSON 中的 drawings 字段
```
