前置知识背景与缘起⏱ 约3分钟

2023年之前，LLM 的输出主要是「给人看的」自由文本。但当开发者试图把 LLM 接入自动化流程时，一个尴尬的问题出现了：模型的输出根本无法被程序解析。

在 LLM 应用的早期（2020-2022），绝大多数使用场景是对话式——用户提问，模型回答。输出的自然语言文本对用户友好，但对下游程序来说是灾难。开发者不得不用正则表达式从模型中「抠」出结构化信息，准确率低、维护成本高。

转折点出现在 2023 年：

  • 2023年6月：OpenAI 在 GPT-3.5 和 GPT-4 API 中引入 Function Calling 功能，允许开发者声明期望的函数签名，模型返回结构化的 JSON 参数。这是结构化输出的第一个工业级解决方案。
  • 2023年11月：OpenAI 在 DevDay 上发布了 JSON Mode，通过设置 response_format={"type": "json_object"}，模型输出被强制约束为有效 JSON。
  • 2024年8月：OpenAI 推出 Structured Outputs，允许开发者直接传入 JSON Schema，模型保证输出符合该 schema。
  • 2025年：约束解码 (Constrained Decoding) 技术成熟，在 token 生成层面就保证格式正确，而非事后验证。

在今天，结构化输出控制已经成为 LLM 应用从「原型」走向「生产」的核心能力。无论是构建 API 服务、数据提取管道、还是多智能体通信系统，没有可靠的结构化输出，一切自动化都无从谈起。

核心概念核心概念⏱ 约4分钟

结构化输出控制不是某个单一技术，而是一套让 LLM 输出从「散文」变成「表格」的方法体系——四种主流方法各有所长，选对方法是第一步。

结构化输出控制 (Structured Output Control) 是指通过设计 prompt 模板、利用 API 参数或引入外部验证机制，将 LLM 的输出约束在预定义的格式（JSON、XML、Markdown 表格、CSV 等）中，使输出可以被程序可靠地解析和处理。

四种主流方法的横向对比：

方法实现方式优点缺点适用场景
Prompt 内嵌格式模板在 prompt 中直接写出期望的输出格式简单、零 API 依赖、跨模型通用格式遵守率不稳定（70-95%），无强制性快速原型、简单格式需求
Function Calling / Tool Use声明函数签名，模型返回结构化的函数参数格式遵守率高（95%+），原生支持需要 API 支持，额外 token 开销API 集成、Agent 工具调用

后处理验证 + 重试解析失败时自动重试，带错误信息可与任何方法组合，最终成功率接近 100%增加延迟和 token 成本对可靠性要求极高的生产环境

边界定义：结构化输出控制不是格式转换——不要试图让模型输出自由文本再解析。最佳实践是从一开始就在 prompt 和 API 层面约束输出格式，把「结构化」作为生成目标而非后处理目标。

核心概念核心原理⏱ 约5分钟

为什么在 prompt 里写一个 JSON 模板，模型就倾向于输出 JSON？答案藏在 LLM 的「格式启动」效应中——模型本质上是补全引擎，你开了什么头，它就会接着写完。

层面一：LLM 是补全引擎 (Completion Engine)

大语言模型从根本上是一个 next-token 预测器。当你给它一个 JSON 开头的序列（如 {"name":），模型在训练数据中见过海量的 JSON 续写模式，它自然会沿着 JSON 语法继续生成。这种效应被称为 格式启动 (Format Priming)——你在 prompt 中嵌入的格式模板就是模型的「起笔位置」。

层面二：条件概率视角

从概率角度看，结构化输出控制本质是在条件概率分布空间中划定约束区域：

条件概率约束模型 $$P(\text{output_format} \mid \text{instruction}, \text{examples}) \approx \frac{\exp(\text{sim}(h_{\text{format}}, h_{\text{context}}))}{\sum_{f' \in \mathcal{F}} \exp(\text{sim}(h_{f'}, h_{\text{context}}))}$$
其中 $h_{\text{format}}$ 是 prompt 中格式模板的语义向量表示，$h_{\text{context}}$ 是整个上下文的向量表示，$\mathcal{F}$ 是模型可用的所有输出格式空间。sim 函数度量格式模板与上下文的匹配度。当 prompt 中包含明确的结构化格式模板时，$h_{\text{format}}$ 在隐空间中形成强「引力井」，模型生成的每个 token 都会被这个引力井牵引向目标格式方向。这就是为什么「在 prompt 中写一个 JSON 模板」比「在 prompt 中说输出 JSON」效果好得多——前者直接激活了模型对 JSON 语法的 token 级预测，而后者只是一个语义级别的请求。

层面三：API 层面的硬约束

对于 JSON Mode 和 Function Calling，API 服务端在解码阶段引入了额外的约束逻辑：在每个时间步，只允许采样满足 JSON 语法（或 JSON Schema）的 token。这相当于在模型的输出分布上施加了一个二值掩码 mask。数学上：

实操三原则（G8 教程法）：

1格式模板比格式指令更有效
✅ 预期：在 prompt 中写出实际的 JSON 结构示例，而非只说「请输出JSON」
⚠️ 常见错误：用自然语言描述期望格式（如「请以JSON格式返回」），模型遵守率约70%；相反，给出具体模板（如 {"name":"...","age":...}），遵守率可达95%+
2选择合适粒度的约束方法
✅ 预期：简单结构用 prompt 模板，复杂 schema 用 Function Calling 或 Structured Outputs
⚠️ 常见错误：对简单任务使用 Structured Outputs，增加了不必要的延迟和复杂度
3永远不要信任单次输出——建立验证-重试闭环
✅ 预期：即使使用 JSON Mode，也要在代码中 try-parse 并在失败时重试
⚠️ 常见错误：假设 JSON Mode 100% 有效。实际上长 JSON 仍可能因 token 截断而无效

实践应用代码实操⏱ 约6分钟

理论看了再多，不如跑一遍代码。从最原始的 prompt 模板到生产级的 Pydantic 类型安全输出，五段代码覆盖所有场景。

1. 基础：Prompt 内嵌 JSON 模板

最基本的 JSON 输出方法——仅靠 prompt 引导 import openai response = openai.chat.completions.create( model="gpt-4o", messages=[{ "role": "system", "content": "你是一个数据提取助手。始终以以下JSON格式返回结果：\n" '{"name": "string", "age": number, "skills": ["skill1","skill2"]}' }, { "role": "user", "content": "张三，28岁，会Python和JavaScript" }] ) # 需要手动 parse，可能失败 import json try: data = json.loads(response.choices[0].message.content) print(data["name"]) # 张三 except json.JSONDecodeError: print("JSON解析失败，需要重试")

2. OpenAI JSON Mode

使用 JSON Mode 保证输出为有效 JSON response = openai.chat.completions.create( model="gpt-4o", response_format={"type": "json_object"}, messages=[{ "role": "system", "content": "你是一个数据提取助手。以JSON格式返回，包含字段：name, age, skills" }, { "role": "user", "content": "张三，28岁，会Python和JavaScript" }] ) data = json.loads(response.choices[0].message.content) # JSON Mode 保证 output 是有效 JSON，但不保证字段名正确

3. Function Calling（工具调用）

使用 Function Calling 进行结构化输出 response = openai.chat.completions.create( model="gpt-4o", messages=[{ "role": "user", "content": "张三，28岁，会Python和JavaScript" }], tools=[{ "type": "function", "function": { "name": "extract_person", "description": "提取人物信息", "parameters": { "type": "object", "properties": { "name": {"type": "string"}, "age": {"type": "integer"}, "skills": { "type": "array", "items": {"type": "string"} } }, "required": ["name", "age", "skills"] } } }], tool_choice={"type": "function", "function": {"name": "extract_person"}} ) import json args = json.loads( response.choices[0].message.tool_calls[0].function.arguments ) print(args) # {"name":"张三","age":28,"skills":["Python","JavaScript"]}

4. Pydantic + Instructor（推荐生产方案）

使用 Instructor 库实现类型安全的结构化输出 import instructor from pydantic import BaseModel, Field from openai import OpenAI client = instructor.from_openai(OpenAI()) class Person(BaseModel): name: str = Field(description="人物姓名") age: int = Field(description="年龄") skills: list[str] = Field(description="技能列表") person = client.chat.completions.create( model="gpt-4o", response_model=Person, messages=[{ "role": "user", "content": "张三，28岁，会Python和JavaScript" }] ) print(person.name) # 张三 (type: str) print(person.age) # 28 (type: int) print(person.skills) # ['Python','JavaScript'] (type: list[str])

5. 后处理验证-重试模式

健壮的生产级重试模式——适用于任何方法 import json import time def structured_call_with_retry(prompt, schema_validator, max_retries=3): for attempt in range(max_retries): response = openai.chat.completions.create( model="gpt-4o", messages=[{"role": "user", "content": prompt}] ) content = response.choices[0].message.content try: data = json.loads(content) if schema_validator(data): return data else: prompt += f"\n上一次输出未通过验证：{data}。请修正。" except json.JSONDecodeError as e: prompt += f"\n上一次JSON解析失败：{e}。请确保输出有效JSON。" time.sleep(1) raise ValueError(f"重试{max_retries}次后仍然失败")
💡 关键洞察：从方案1到方案5，代码复杂度递增但可靠性也递增。在原型阶段可以从方案1开始，但一旦进入生产环境，至少应使用方案3（Function Calling），最佳实践是方案4（Instructor）配合方案5（重试模式）。

关键发现：

  • Prompt 模板法有明显的模型差异：GPT-4o 的纯 prompt JSON 遵守率（94.2%）显著高于 Gemini（89.3%），反映模型训练数据中 JSON 模式的覆盖度差异。
  • Function Calling/Structured Outputs 是游戏规则的改变者：一旦启用 API 层面的约束，跨模型的格式遵守率都跃升到 95%+，模型差异几乎消失。
  • Schema 合规率 ≠ JSON 有效率：JSON Mode 保证了 99.7% 的 JSON 语法正确，但只有 92.1% 符合你的字段 schema——字段名写错、缺少必填字段等问题依然存在。这就是为什么 Structured Outputs（允许指定完整 JSON Schema）价值巨大。

其中 $R_0$ 是 2022 年的基准可靠性（约 75%），$\lambda$ 是进步速率常数。log(1-R) 与时间 t 近似线性关系，说明结构化输出的可靠性正在指数级收敛到 100%。按当前趋势，到 2026 年，生产环境的结构化输出将基本实现「零信任但零失败」——你仍然需要验证，但验证几乎永远不会失败。

从合同文档中提取结构化信息 class ContractInfo(BaseModel): parties: list[str] = Field(description="合同方名称列表") effective_date: str = Field(description="生效日期 YYYY-MM-DD") amount: float = Field(description="合同金额") clauses: list[str] = Field(description="关键条款摘要") info = client.chat.completions.create( model="gpt-4o", response_model=ContractInfo, messages=[{"role":"user","content": contract_text}] )

场景三：表单自动填充

从用户对话中提取信息填充表单字段。核心技巧：将表单的每个字段定义为 Pydantic Field，利用 LLM 的多轮对话能力逐步收集缺失字段。

场景五：多智能体通信协议

在 Multi-Agent 系统中，Agent 之间的消息必须是严格结构化的，否则解析失败会导致整个协作链断裂。推荐使用统一的 Message Schema 作为 Agent 间通信格式。

实践应用实践案例⏱ 约4分钟

一个真实的简历解析器项目——从 1000 份自由格式的简历中提取结构化字段。纯手工 prompt 准确率 73%，引入 Instructor + Structured Outputs 后跃升到 96%。

背景：某招聘平台需要从用户上传的 PDF/Word 简历中提取结构化数据（姓名、联系方式、工作经历、教育背景、技能列表），用于自动填充简历数据库。

项目架构：

简历解析器——完整 Pydantic Schema 定义 from pydantic import BaseModel, Field from typing import Optional from datetime import date class WorkExperience(BaseModel): company: str position: str start_date: str end_date: Optional[str] = None responsibilities: list[str] class Education(BaseModel): school: str degree: str major: str graduation_year: int class Resume(BaseModel): name: str = Field(description="候选人姓名") email: Optional[str] = Field(description="邮箱地址", default=None) phone: Optional[str] = Field(description="电话号码", default=None) years_of_experience: Optional[int] = Field(description="总工作年限", default=None) work_experiences: list[WorkExperience] = Field( description="工作经历列表，按时间倒序" ) educations: list[Education] = Field(description="教育经历列表") skills: list[str] = Field(description="技能列表") summary: Optional[str] = Field(description="个人总结", default=None)

方案演化：

  • V1 (Prompt 模板法)：在 prompt 中写 JSON 模板，准确率约 73%。问题：嵌套数组（work_experiences）经常格式错误，日期格式不统一。
  • V2 (JSON Mode + 重试)：准确率提升到 88%。JSON 语法问题解决，但 schema 合规率仍不够高。
  • V3 (Instructor + GPT-4o Structured Outputs)：准确率 96%。嵌套结构、枚举字段完全合规，skills 字段召回率从 78% 提升到 94%。
图：简历解析器三版本准确率对比

成本分析：V1 平均 1200 tokens/份 → $0.006/份；V3 平均 2000 tokens/份 → $0.011/份（含重试）。1000 份简历，从 $6 增加到 $11——但省下的 23% 人工审核成本约 $500/月。

💡 经验教训：对于嵌套结构（如工作经历列表），纯 prompt 模板几乎不可能达到生产级可靠性。一定要使用 Function Calling 或 Structured Outputs。另外，对于可选字段，务必将 default 设为 None 或合理默认值，避免模型为了「填满」所有字段而编造信息（幻觉）。

风险与挑战潜在风险⏱ 约4分钟

你以为用了 JSON Mode 就万事大吉？六种常见陷阱可能在你不经意间让整个输出管道崩溃——每一行代码都在与 LLM 的可变性博弈。
风险类型描述影响程度缓解策略
格式幻觉 (Format Hallucination)模型虚构不存在的 JSON 字段或属性名🔴 高使用 Structured Outputs 约束 schema；对额外字段进行裁剪
不完整 JSON输出被上下文窗口截断，JSON 括号未闭合🔴 高设置 max_tokens 为期望输出的 1.5 倍；对截断 JSON 进行补全重试
字段类型不匹配模型将 number 输出为 string，或将 array 输出为 string 化的数组🟡 中后处理阶段进行类型强制转换；使用 Pydantic 的类型验证
Token 限制截断输出超长 JSON（如大量数组元素）被 token 上限截断🟡 中分批请求；对列表类输出设置元素数量上限
嵌套对象复杂度深层嵌套（3+ 层）的 JSON 中内层字段容易出错或丢失🟡 中减少 Schema 嵌套深度（≤2 层）；拆分为多次独立请求
编码/本地化问题中文字符在 JSON 中被 escape 为 \uXXXX，或日期格式与预期不符🟢 低统一指定日期格式（ISO 8601）；在 prompt 中明确字符编码要求
风险评估公式：系统可靠性 $$R_{\text{system}} = R_{\text{format}} \times R_{\text{schema}} \times R_{\text{field\_value}} \times (1 - P_{\text{truncation}})$$
系统的整体可靠性是各环节可靠性的乘积。假设 JSON Mode 下：$R_{\text{format}} = 0.997$，$R_{\text{schema}} = 0.921$，$R_{\text{field\_value}} = 0.935$，$P_{\text{truncation}} = 0.02$。则 $R_{\text{system}} = 0.997 \times 0.921 \times 0.935 \times 0.98 \approx 0.841$。即即使使用 JSON Mode，仍有约 16% 的请求需要重试处理。加上重试机制后，2 次重试可将整体成功率提升至约 97.5%。这就是为什么验证-重试是生产环境不可或缺的组件。

风险与挑战伦理与安全⏱ 约3分钟

结构化输出的确定性特征也带来了新的安全风险——攻击者可以利用格式约束来诱导模型输出敏感信息，或通过精心构造的格式要求绕过内容过滤机制。

1. 格式注入攻击 (Format Injection)

攻击者可能通过构造特定的格式要求来绕过内容安全策略。例如，在 JSON 输出要求中嵌入恶意脚本或命令注入代码。防御策略：

  • 对输出进行严格的 schema 验证，拒绝未预期的字段
  • 对输出内容进行二次清洗（HTML 转义、特殊字符过滤）
  • 在生产环境中使用白名单机制，只允许预定义的输出结构

2. 信息泄露风险

结构化输出可能无意中暴露系统内部数据结构或敏感信息。例如，当要求模型输出 JSON 格式时，模型可能在错误信息或调试信息中泄露内部 schema。防御策略：

  • 使用 Pydantic 的 exclude 参数隐藏敏感字段
  • 在响应中使用统一的错误格式，避免暴露内部细节
  • 对返回的数据进行脱敏处理

3. 公平性考虑

当结构化输出用于决策系统时，需要确保输出格式不会引入或放大偏见。例如，在招聘系统中，如果 JSON 输出的字段定义本身带有性别或年龄相关的偏见，可能导致不公平的决策。

发展前景发展前景⏱ 约3分钟

从「手动写 JSON 模板」到「声明式 Schema 驱动」——结构化输出控制正在从「工程实践」走向「编程语言级特性」。

趋势一：Schema 即代码

未来，结构化输出的 Schema 定义将成为 AI 应用的核心资产。像 BAML 这样的工具正在将 Schema 定义提升到编程语言级别——定义一次 Schema，自动生成类型安全的代码、API 文档和验证逻辑。

趋势二：约束解码内置化

当前的约束解码（Constrained Decoding）还需要额外工具（如 Outlines）支持。未来，主流模型（尤其是开源模型）将原生支持约束解码，通过 API 参数直接指定输出格式。

趋势三：多模态结构化输出

结构化输出正在从纯文本扩展到多模态领域。例如，输出包含文本、图像 URL、音频描述的结构化对象，或者直接输出编程语言的 AST（抽象语法树）。

趋势四：自动 schema 推断

LLM 将能够根据少量示例自动推断出最优的输出 Schema，减少开发者的手动定义工作。这将进一步降低结构化输出的使用门槛。

常见误区常见误区⏱ 约3分钟

结构化输出看起来简单，但踩坑无数。这五个误区每年浪费开发者数万小时——别让它们绊倒你。
1误区：JSON Mode 能解决所有问题
⚠️ 事实：JSON Mode 只保证 JSON 语法正确，不保证字段名正确、类型正确或字段值正确。你仍然需要验证每个字段。
2误区：嵌套结构越深越好
⚠️ 事实：嵌套超过 2-3 层后，模型的格式遵守率急剧下降。建议将复杂结构拆分为多次调用。
3误区：不需要重试机制
⚠️ 事实：即使使用 Function Calling，仍有 2-5% 的请求需要重试。生产环境必须实现验证-重试闭环。
4误区：字段越多越好
⚠️ 事实：字段越多，模型出错的概率越高。只定义真正需要的字段，可选字段设置合理默认值。
5误区：格式模板只需写一次
⚠️ 事实：随着模型版本升级或任务变化，格式模板可能需要调整。建议将格式模板作为配置管理，而非硬编码。

术语表关键术语表⏱ 约2分钟

把关键术语整理在一起，方便快速查阅和复习。
结构化输出控制 (Structured Output Control)
通过设计 prompt 模板、利用 API 参数或引入外部验证机制，将 LLM 输出约束在预定义格式中的方法体系。
JSON Mode
OpenAI API 的响应格式参数，设置后模型保证输出为有效 JSON。
Function Calling
LLM API 的工具调用功能，允许开发者声明函数签名，模型返回结构化的函数参数。
约束解码 (Constrained Decoding)
在 token 生成层面就保证输出符合指定格式约束的技术。
格式启动 (Format Priming)
在 prompt 中嵌入格式模板，引导模型生成符合该格式的输出。
Schema 合规率 (Schema Compliance Rate)
输出符合预期 JSON Schema 的比例，包括字段名正确、类型正确、必填字段齐全。
