前置知识背景与缘起⏱ 约3分钟

从 GPT-2 的 1024 tokens 到 Gemini 1.5 Pro 的 100万+ tokens——上下文窗口的膨胀速度远超摩尔定律，但「更大」真的意味着「更好」吗？

2019年，GPT-2 的上下文窗口只有 1024 个 token。这意味着你喂给模型的内容，连一篇中等长度的维基百科文章都放不下。当时处理长文本的唯一方法是将文本切成碎片、分次处理。到 2023年，Claude 2 率先突破了 100K tokens 大关，可以用一次 API 调用「吞下」整本《了不起的盖茨比》。而到了 2024年初，Gemini 1.5 Pro 更是将上下文窗口推进到了惊人的 100 万+ tokens——相当于一次性处理 1500 页的PDF文档。

但上下文窗口的扩张并非没有代价。2023年，Liu et al. 发表在 arXiv 上的经典论文 "Lost in the Middle: How Language Models Use Long Contexts" 揭示了一个令人不安的事实：当文本被放置在上下文窗口的中间位置时，模型提取信息的能力会显著下降。也就是说，即使模型声称拥有 128K 的上下文窗口，它对第 64K 位置附近信息的理解能力可能远不如对开头和结尾的理解。

这一发现从根本上改变了我们对上下文窗口的理解范式：问题不再是「能不能塞进去」，而是「塞进去之后模型能不能有效理解」。这催生了五个核心的长文本处理策略——分块滑动窗口、层次化摘要、检索增强生成(RAG)、上下文压缩和 Prompt 缓存——它们共同构成了现代长文本提示工程的工具箱。

核心概念核心概念⏱ 约5分钟

处理 10 万字的长文档，你可以在「分块—摘要—再摘要」的流水线上解决，也可以「只检索相关段落扔进上下文」——这五种策略构成了长文本提示工程的全部武器。

面对超出上下文窗口的长文本，有五种核心处理策略，它们各自有不同的适用场景和代价：

策略一：分块/滑动窗口 (Chunking / Sliding Window)

将长文本按固定大小（如 512 tokens）切成多个块（chunk），每个块之间保留一定重叠（如 50 tokens 重叠），逐块送入模型处理，最后汇总结果。这是最朴素的方案，但分块边界的语义断裂是最大的问题——一句话被切成两半，模型就无法完整理解。

策略二：层次化摘要 (Hierarchical Summarization)

先对每个 chunk 独立生成摘要，再将所有 chunk 的摘要拼接后再次摘要——重复此过程直到摘要长度可接受。这种方法天然适合需要对全文有整体理解的任务，缺点是每次摘要都会丢失信息，层级越深信息越少。

策略三：检索增强生成 (RAG)

不把整篇文档放入上下文，而是将文档分块后做向量嵌入，用户提问时只检索最相关的 k 个 chunk 放入上下文。这是目前工业界最主流的长文本处理方案。核心挑战在于检索精度——召回的 chunk 如果不相关，模型就「巧妇难为无米之炊」。

策略四：上下文压缩 (Context Compression)

使用一个小模型（或 LLM 自身）对长文本进行压缩——去除冗余词句、保留关键信息——然后再送入目标 LLM。代表工具是微软的 LLMLingua。这种方法在 token 成本上有显著优势，但压缩过程本身可能丢失微妙的语义信息。

策略五：Prompt 缓存 (Prompt Caching)

当多轮对话或多次查询共享同一段长上下文时，模型服务商（如 Anthropic）允许你缓存已处理过的上下文计算结果，后续查询只需支付增量 token 费用。这本质上是一个成本优化策略而非处理策略，但在实际工程中至关重要。

策略核心思想token 成本信息保真度最佳场景
分块/滑动窗口切分+独立处理+汇总高中结构化提取
层次化摘要层层摘要递归中中低全文概括理解
RAG检索+仅注入相关块低中高问答/信息检索

在实践中，这五种策略往往不是「选一个」而是「组合使用」——例如 RAG + 层次化摘要的组合（先用 RAG 检索，再对检索结果摘要）是当前公认的最佳工程方案之一。

核心概念核心原理⏱ 约5分钟

为什么上下文窗口不是越大越好？答案藏在 Transformer 自注意力机制的 O(n²) 复杂度、「迷失在中间」现象和 token 成本的三重诅咒中。

理解上下文窗口管理的必要性，需要从三个底层原理入手：

原理一：注意力复杂度的 O(n²) 诅咒

Transformer 的自注意力机制要求序列中的每个 token 计算与所有其他 token 的注意力权重。这意味着如果上下文有 n 个 token，计算量就是 O(n²)。从 4K 到 128K，计算量膨胀了 1024 倍。这就是为什么长上下文模型需要更强大的硬件、更长的推理时间和更高的 API 价格。即使模型厂商通过 FlashAttention、Ring Attention 等优化大幅降低了常数因子，平方级的增长趋势无法消除。

原理二：「迷失在中间」(Lost in the Middle)

Liu et al. (2023) 通过大量实验证明了模型的注意力分布极度不均衡：模型对上下文开头（primacy effect）和结尾（recency effect）的信息更关注，而对中间位置的信息理解能力显著下降。这种「U 形」注意力曲线意味着，如果你把关键信息放在 128K 上下文的第 60K 位置，模型可能完全「看不到」它。这对 RAG 系统的 chunk 排序策略有直接启示——最相关的 chunk 应该放在靠近上下文开头或结尾的位置。

原理三：Token 成本的线性增长

API 按 token 计费，上下文越长，每次调用成本越高。以 GPT-4o 为例，输入 token 单价为 $2.50/1M tokens。一次填满 128K 上下文的调用需要 $0.32，如果每天调用 1000 次，月度成本高达 $9600。这还不包括输出 token。因此，用最少的 token 传递最多的有效信息——即 信息密度优化 (Information Density Optimization)——是提示工程师的核心能力。

公式1: 有效上下文利用率 $$\eta = \frac{T_{\text{useful}}}{T_{\text{total}}} \times P_{\text{attention}}(pos)$$
其中 $T_{\text{useful}}$ 是传递有效信息的 token 数，$T_{\text{total}}$ 是总输入的 token 数，$P_{\text{attention}}(pos)$ 是模型对位置 $pos$ 的注意力权重（受 Lost in the Middle 效应影响）。例如：在 128K tokens 中只有 8000 tokens 是相关信息且位于中间位置（注意力权重约 0.3），则 $\eta = 8000/128000 \times 0.3 \approx 1.9\%$——也就是说，98% 的上下文窗口实际上被浪费了。这个公式解释了为什么「只检索相关 chunk 的 RAG」比「全量灌入」在大多数任务上更高效。
1信息密度优先于上下文长度
✅ 预期：每 1000 tokens 的 prompt 应包含至少一个明确的指令或关键信息点
⚠️ 常见错误：在 prompt 中复制大段无关背景文本，模型被噪声淹没
2关键信息放在开头或结尾
✅ 预期：最重要的上下文信息应位于 prompt 的前 10% 或后 10% 位置，可提升 20-30% 的信息提取准确率
⚠️ 常见错误：关键信息均匀分布在整个上下文中，模型对中间部分的理解出现明显盲区
3先检索，再推理
✅ 预期：RAG 模式下 token 利用率可达 40-70%，远高于全量输入模式的 2-5%
⚠️ 常见错误：不加筛选地将整篇文档塞入 context，忽略检索环节的价值

核心工具代码实操⏱ 约6分钟

理论说一百遍不如跑一遍代码。这一节你将亲手实现从文档分块到 RAG 问答的完整流水线。

示例1：LangChain 递归文本分割器

LangChain RecursiveCharacterTextSplitter 基础用法 from langchain.text_splitter import RecursiveCharacterTextSplitter text_splitter = RecursiveCharacterTextSplitter( chunk_size=512, chunk_overlap=50, separators=["\n\n", "\n", "。", ".", " ", ""] ) with open("long_document.txt", "r", encoding="utf-8") as f: document = f.read() chunks = text_splitter.split_text(document) print(f"文档被分割为 {len(chunks)} 个块") print(f"平均块大小: {sum(len(c) for c in chunks)/len(chunks):.0f} 字符")

示例2：滑动窗口实现

自定义滑动窗口分块器 def sliding_window_chunks(text, window_size=500, step=400): chunks = [] text_len = len(text) for start in range(0, text_len, step): end = min(start + window_size, text_len) chunk = text[start:end] if len(chunk) > 50: chunks.append((start, chunk)) return chunks text = "这是一段非常长的文本..." * 1000 chunks = sliding_window_chunks(text, window_size=500, step=400) print(f"滑动窗口生成 {len(chunks)} 个块，重叠率 {1-400/500:.0%}")

示例3：层次化摘要 (Map-Reduce)

LangChain Map-Reduce 摘要链 from langchain.chains.summarize import load_summarize_chain from langchain_openai import ChatOpenAI llm = ChatOpenAI(model="gpt-4o-mini", temperature=0) chain = load_summarize_chain( llm, chain_type="map_reduce", verbose=False ) from langchain.schema import Document docs = [Document(page_content=chunk) for chunk in chunks[:20]] summary = chain.invoke(docs) print(summary['output_text'])

示例4：基于 FAISS 的 RAG 流水线

端到端 RAG 问答流水线 from langchain_openai import OpenAIEmbeddings from langchain_community.vectorstores import FAISS from langchain.chains import RetrievalQA from langchain_openai import ChatOpenAI embeddings = OpenAIEmbeddings(model="text-embedding-3-small") texts = [chunk for _, chunk in chunks[:100]] metadatas = [{"position": i} for i in range(len(texts))] vectorstore = FAISS.from_texts(texts, embeddings, metadatas=metadatas) qa_chain = RetrievalQA.from_chain_type( llm=ChatOpenAI(model="gpt-4o", temperature=0), chain_type="stuff", retriever=vectorstore.as_retriever(search_kwargs={"k": 4}) ) question = "文档中提到的核心方法论是什么？" answer = qa_chain.invoke(question) print(f"Q: {question}") print(f"A: {answer['result']}")

示例5：LLMLingua 上下文压缩

使用 LLMLingua 压缩长 prompt from llmlingua import PromptCompressor compressor = PromptCompressor( model_name="microsoft/llmlingua-2-bert-base-multilingual-cased-meetingbank", use_llmlingua2=True, ) long_context = "这是一段非常冗余、包含大量无用修饰词的文本..." * 50 compressed = compressor.compress_prompt( long_context, rate=0.5, force_tokens=['核心', '关键', '重要'], ) original_tokens = len(long_context) compressed_tokens = len(compressed['compressed_prompt']) print(f"压缩率: {compressed_tokens/original_tokens:.1%}") print(f"节省 token: {original_tokens - compressed_tokens}")

示例6：Claude Prompt Caching

Anthropic Prompt Caching API 示例 import anthropic client = anthropic.Anthropic() response = client.messages.create( model="claude-sonnet-4-20250514", max_tokens=1024, system=[{ "type": "text", "text": open("system_prompt.txt").read(), "cache_control": {"type": "ephemeral"} }], messages=[{ "role": "user", "content": [{ "type": "text", "text": open("long_document.txt").read(), "cache_control": {"type": "ephemeral"} }] }] ) print(f"缓存创建token: {response.usage.cache_creation_input_tokens}") print(f"缓存读取token: {response.usage.cache_read_input_tokens}") print(f"节省成本: {response.usage.cache_read_input_tokens / 1e6 * 0.375:.4f} USD")

实践应用实践应用⏱ 约5分钟

从 500 页技术手册的智能问答，到头天会议录音的自动摘要——长文本处理的五个典型场景，每个都有独特的技术选型和工程考量。

场景一：书籍摘要 (Book Summarization)

1层次化摘要 + Map-Reduce
✅ 方案：先逐章摘要、再跨章主题合并、最后生成全书摘要
⚠️ 注意：仅 Map-Reduce 一层不够，书籍通常需要 2-3 层递进摘要才能保持逻辑连贯
  • 推荐 chunk_size：2000-4000 tokens（保持段落完整性）
  • 摘要策略：每章摘要→主题聚类→跨主题综合
  • 输出要求：生成「逐章要点 + 主题脉络 + 全书总结」三层结构

场景二：法律文档审查 (Legal Document Review)

2RAG + 语义分块 + 精确检索
✅ 方案：按条款号分块，嵌入后支持精确条款检索，关键条款保留原文
⚠️ 不得对法律条款做摘要——任何改写都可能改变法律含义，法律文档中原文即真理

场景三：代码库分析 (Codebase Analysis)

3AST 感知分块 + RAG
✅ 方案：按函数/类边界分块，保留 import 依赖关系，嵌入后支持语义搜索
⚠️ 不能按 token 数切分——会破坏函数边界，导致模型无法理解代码逻辑

场景四：会议转录处理 (Meeting Transcript Processing)

会议录音转文字后通常是 1-3 万字的对话文本，核心需求是提取决议、行动项和关键观点。推荐方案：先用 RAG 检索特定议题，再用层次化摘要生成会议纪要。注意：对话文本中大量「嗯」「那个」「就是说」等口语填充词会稀释 token 密度，建议预处理时用 LLMLingua 做初步压缩。

场景五：研究论文合成 (Research Paper Synthesis)

需要对比多篇论文（通常 5-20 篇，每篇 5000-15000 字）。推荐方案：每篇独立 RAG 索引→跨论文检索→对比摘要链。核心挑战在于保持跨论文引用的准确性和一致性。

实践应用实践案例⏱ 约4分钟

一本 500 页的技术手册，500+ 个技术问题——如何用 RAG 实现「一秒检索，精准回答」？这个真实案例揭开了从原型到上线的每一层细节。

案例：500 页技术手册的智能问答系统

背景：某工业自动化设备厂商拥有一本 500 页的 PDF 技术手册，客服团队每天需要花费大量时间翻阅手册查找答案。目标是构建一个能回答「设备X 的错误码 Y22 怎么排查？」这类问题的 RAG 问答系统。

实施方案：

  • 文档预处理：使用 Unstructured.io 解析 PDF，保留表格和图片标题（图片暂时不做 OCR）
  • 分块策略：RecursiveCharacterTextSplitter，chunk_size=800 tokens，chunk_overlap=100 tokens。关键优化：为每个错误码说明、每个配置参数单独设定 chunk 边界（通过自定义分隔符实现）
  • 嵌入模型：OpenAI text-embedding-3-large（3072 维），共生成 6,200 个向量
  • 向量存储：FAISS，本地磁盘持久化
  • 检索策略：top_k=5，相似度阈值 0.75（低于阈值触发「降级策略」——扩大检索到全手册的关键词匹配）
  • LLM：GPT-4o，temperature=0，system prompt 中明确「只在提供的文档中找答案，找不到就说找不到」

上线前测评指标：

指标V1(原型)V2(优化后)改进
检索召回率 (Recall@5)82%94%+12%
答案准确率 (Correctness)76%91%+15%
幻觉率 (Hallucination Rate)18%5%-13%
每查询平均 token 消耗3,2001,800-44%
每查询平均成本$0.012$0.006-50%
平均响应时间4.2s2.1s-50%

V1→V2 的关键改进点：

  • 将 chunk_overlap 从 0 调整为 100，解决了「关键信息恰好在分割边界」导致的召回失败
  • 为错误码表格单独创建 chunk，避免表格跨页分割
  • 将 system prompt 从泛化的「你是技术助手」改为领域定制的「你是XX设备技术支持工程师，严格按照提供的文档内容回答问题」
  • 添加相似度阈值和降级策略，减少在 RAG 找不到时的幻觉
图：RAG系统 V1 vs V2 核心指标对比
这个案例的核心启示：RAG 系统 80% 的性能来自于「chunk 策略」和「检索质量」——LLM 本身只是一个「优秀的答案组织者」，但如果检索到的上下文是错的，任何 LLM 都救不了。

风险与挑战伦理与安全⏱ 约3分钟

你把客户的 500 页合同上传到 RAG 系统做智能问答——但你考虑过隐私泄露、数据留存和二次使用的伦理问题吗？

1. 长文档处理中的数据隐私

当一个系统需要处理长文档（合同、病历、财务报表）时，这些文档通常包含大量个人身份信息 (PII) 和商业机密。在将文档送入 LLM（尤其是通过 API 调用的第三方模型）之前，必须考虑：

  • API 数据传输：文档内容是否经过了第三方服务器？OpenAI、Anthropic 等厂商的隐私政策是否允许你的使用场景？
  • 本地部署 vs 云端：对于高度敏感的文档，应优先使用本地部署的开源模型（如 Llama 3.3 via Ollama），确保数据不出企业内网。
  • 数据脱敏：在分块和嵌入之前，应先使用 NER + 正则替换脱敏姓名、身份证号、银行卡号等 PII。

2. 文档分析的知情同意

当分析涉及个人文档（如简历、求职信、法律文件），需要确保文档所有者知晓并同意其文档被 AI 系统处理。尤其是在招聘、信贷审批等场景，AI 辅助分析未经当事人同意可能构成伦理违规。

3. RAG 系统中的数据留存

RAG 系统将文档分块嵌入后存储在向量数据库中。需要明确：

  • 留存期限：嵌入向量和原始 chunk 应该保留多久？是否有定期清理机制？
  • 删除权利：用户是否有权要求删除其文档的嵌入向量？（技术上可以实现——从 FAISS/ChromaDB 中按 metadata 删除特定来源的向量）
  • 二次使用：嵌入向量是否会被用于训练或改进模型？这需要明确告知并获得同意。
✓伦理审查清单
✅ 长文档在上传前是否进行了 PII 脱敏？
✅ API 调用是否使用了零数据留存模式（如 OpenAI API 的 data usage opt-out）？
✅ 向量数据库是否支持按来源删除嵌入？（metadata 中应包含 source_doc_id）
⚠️ 不要假设「文档只是暂存在向量库里」——嵌入向量可以反向推断出原文的语义信息

发展演进发展前景⏱ 约3分钟

如果 Ring Attention 让 100 万 token 成为「基本盘」，如果混合 RAG+长上下文让「任意长度」成为可能——那么上下文窗口的未来会是什么样子？

趋势一：无限上下文 via Ring Attention

Ring Attention (Liu et al., 2023) 通过将长序列的计算分布在多个设备上（如同环形接力），理论上可以处理任意长度的上下文，且计算复杂度从 O(n²) 优化为 O(n)。虽然目前实现仍有工程限制，但这代表了「不再需要上下文窗口」的技术方向。

趋势二：流式上下文 (Streaming Context)

Google DeepMind 的 StreamingLLM 和 MIT 的 Infini-attention 提出了一种新的注意力范式：模型不再需要「一次性看到所有上下文」，而是像人类阅读一样逐段处理，同时维护一个「压缩记忆」。这使得理论上无限的上下文成为可能——模型只需记住压缩后的关键信息，而非原始的每个 token。

趋势三：递归记忆 Transformer (Recurrent Memory Transformer)

DeepMind 的工作 Borgeaud et al. (2022) 展示了通过在 Transformer 中引入显式的记忆 token，模型可以在处理后续 chunk 时「回忆」前面 chunk 的信息。这种「读一段、记一段」的模式让模型在长文本上的表现显著优于传统方案。

趋势四：混合 RAG + 长上下文

当前最务实的趋势是：不是二选一，而是 RAG 用于粗略检索 + 长上下文用于精细理解。先用 RAG 定位相关区域（节省 95% token），再将相关区域的原始文本完整送入 LLM（保证信息保真度）。Anthropic 的 contextual retrieval 和 Google 的 RAG + Long Context 方案都在朝这个方向发展。

时间线标志事件上下文范式
2024-2025Gemini 1.5 Pro 1M tokens 商用大上下文 + RAG 混合
2025-2026（预测）开源模型达到 256K-512KRAG 仍是成本最优解
2026-2027（预测）Ring Attention 商用，10M+ tokensRAG 退居二线，混合方案为主

核心概念常见误区⏱ 约3分钟

「上下文越大答案越好」「RAG 一定优于长上下文」「chunk 随便切都行」——这五个误区，每年浪费开发者上百万美元的 token。

误区 1：「更大的上下文 = 更好的答案」

这是最昂贵也最常见的误解。Lost in the Middle 现象证明，更大的上下文不一定带来更好的信息提取能力。在 200K 上下文中把问题答案藏在第 100K 位置，模型的准确提取率可能比 10K 上下文中答案在第 5K 位置更低。上下文窗口是「容量」，不是「能力」。

误区 2：「RAG 一定比长上下文好」

RAG 的优势在于成本和效率，但它有一个致命弱点：检索失败时模型完全无法回答。如果你的知识库是高度关联的（如法律判例关系），RAG 的切片式检索会丢失上下文关联。此时长上下文全量加载可能更合适——当然，前提是你能承担成本。结论：取决于任务类型，不是非此即彼。

误区 3：「全塞进去就好」

把整本手册、整条对话历史、所有相关文档不加筛选地全部塞进 128K 上下文——这种做法同时犯了「成本爆炸」「注意力稀释」「Lost in the Middle」三重错误。即使你不在乎成本，信息密度不足的 prompt 也会显著降低回答质量。

误区 4：「分块是小事，随便切切就行」

分块策略是整个长文本处理系统的基石。chunk_size 选错了、chunk_overlap 设为 0、不考虑文档结构的切分——任何一个错误都可能让你的 RAG 系统的检索召回率下降 20-30%。chunk_size 的经验法则：512-1024 tokens 适合问答，2000-4000 tokens 适合摘要。

!Debug 技巧
RAG 答案质量差 → 先检查检索结果是否相关（并非 LLM 的问题）→ 调整 chunk_size 和 embedding 模型
长上下文回答遗漏关键信息 → 检查信息所在位置是否在「中间盲区」→ 将关键信息移至开头或末尾
成本失控 → 统计 prompt 中「有效 token」比例 → 如果低于 20%，考虑用 RAG 替代全量输入

核心概念学习路径⏱ 约3分钟

从动手实验不同 chunk_size 的效果，到亲手搭建一个完整的 RAG 问答系统——三个阶段的实操路线带你从 0 到 1。

阶段 1：动手实验 Chunking (30 分钟)

  • 取一篇 5000 字的文章，用 LangChain RecursiveCharacterTextSplitter 分别按 chunk_size=256/512/1024/2048 切分
  • 将同一段关键信息放在不同分块策略下的不同位置，观察模型的回答准确度
  • 体会「chunk 过大→信息稀释」「chunk 过小→语义断裂」的权衡

必备工具：Jupyter Notebook / Google Colab + LangChain + OpenAI API (或本地 Ollama)

阶段 2：构建 RAG 流水线 (1 小时)

  • 准备一个 10-50 页的 PDF 文档（可以是技术文档、论文或合同）
  • 使用 Unstructured.io 或 PyPDF2 解析文档
  • 用 RecursiveCharacterTextSplitter 分块，OpenAI Embeddings 做向量嵌入，FAISS/ChromaDB 做向量存储
  • 搭建 RetrievalQA 链，测试 20 个覆盖不同章节的问题
  • 记录检索召回率和答案准确率，迭代优化 chunk_size 和 top_k

必备工具：LangChain + FAISS/ChromaDB + OpenAI/本地 Embedding 模型

阶段 3：实现层次化摘要 (2 小时)

  • 选择一篇 50-100 页的书籍或长报告
  • 按章分块，对每章生成摘要 (Map 阶段)
  • 将所有章摘要在一定 token 预算内合并，生成二级摘要 (Reduce 阶段)
  • 如果二级摘要仍然超出 token 限制，递归 Reduce
  • 对比直接截断（只读前 N tokens）vs 层次化摘要的效果差异

必备工具：LangChain load_summarize_chain (chain_type="map_reduce" 或 "refine")
