前置知识背景与缘起⏱ 约3分钟

2020年，GPT-3 的论文中一个惊人的发现改变了 NLP 世界：你不需要为每个任务训练一个模型，只需在 prompt 里给几个例子，模型就能「理解」你要什么。

在 GPT-3 出现之前（2020年以前），自然语言处理的主流范式是 「预训练 + 微调」(pre-train + fine-tune)：先在大规模语料上预训练一个语言模型，然后针对每个具体任务（情感分析、翻译、摘要等）收集标注数据、微调模型参数。这种方法需要大量标注数据，且每个任务都要维护一个独立的模型副本。

2020年6月，OpenAI 发布了 GPT-3（Brown et al., 2020），展示了令人震惊的能力：在不更新任何模型参数的情况下，仅仅通过在 prompt（提示文本）中描述任务或给出少量示例，1750亿参数的模型就能完成翻译、问答、代码生成等数十种任务。这种范式被称为 in-context learning（上下文学习）。

根据 prompt 中是否包含任务示例，in-context learning 被分为三个梯度：

  • 零样本 (Zero-shot)：prompt 中只描述任务，不提供任何示例。
  • 单样本 (One-shot)：prompt 中提供一个示例。
  • 少样本 (Few-shot)：prompt 中提供少量示例（通常 2-8 个）。

这一发现开启了提示工程 (Prompt Engineering) 的新纪元——与其训练模型，不如训练 prompt。此后，思维链 (Chain-of-Thought, Wei et al., 2022)、指令微调 (Instruction Tuning)、RLHF 等技术相继出现，但零样本/少样本提示始终是提示工程最基本、最常用的工具。

核心概念核心概念⏱ 约4分钟

如果把大语言模型想象成一个通晓万物的实习生，zero-shot 就是直接告诉他「做X」，few-shot 则是给他看几个你做过的例子然后说「照这个做」。

零样本提示 (Zero-shot Prompting) 指在不提供任何任务示例的情况下，仅通过指令文本让模型执行任务。模型完全依赖其预训练阶段学到的知识和指令理解能力来完成推理。

少样本提示 (Few-shot Prompting) 指在 prompt 中提供少量（通常 2-8 个）输入-输出示例对 (demonstrations)，让模型通过示例模式「学会」如何完成任务，然后对新的输入进行推理。

两者的核心差异可以从以下几个维度理解：

维度零样本 (Zero-shot)少样本 (Few-shot)
示例数量01-8（典型值 3-5）
prompt 长度短，仅指令较长，含示例上下文
token 消耗低中等（示例占据 token）
适用场景简单分类、翻译、摘要复杂推理、特定格式输出、细粒度分类
对指令质量的依赖极高——指令必须极其清晰中等——示例可弥补指令模糊
模型规模要求大模型（通常≥7B）效果好中等模型（≥1B）即可受益
核心挑战指令歧义、任务理解偏差示例偏差(label bias)、示例顺序敏感

边界定义：零样本/少样本的核心特点是 模型参数不更新（即不进行梯度下降）。这与微调 (fine-tuning) 有本质区别——微调需要更新模型参数。在提示工程语境中，零样本和少样本都属于 in-context learning 的范畴。

核心概念核心原理⏱ 约5分钟

模型在训练时从未「见过」你的任务，但为什么给它几个例子就能做？答案藏在 Transformer 的注意力机制和语言模型在预训练阶段形成的「模式匹配直觉」中。

零样本/少样本提示能工作的底层原理可以从三个层面理解：

层面一：语言建模即隐式多任务学习

在预训练阶段，语言模型的目标是预测下一个 token。Radford et al. (2019) 和 Brown et al. (2020) 指出，互联网文本中天然包含大量「任务示例」——例如论坛中的问答对、代码文档中的输入输出示例、学术论文中的摘要。当模型学会预测下一个 token 时，它同时也隐式学会了执行这些任务。因此，当你给出一个任务描述或示例时，模型实际上是在做它训练时就在做的事：根据前文模式续写后续内容。

层面二：Transformer 的上下文关联能力

Transformer 的自注意力机制允许每个 token 关注输入序列中的所有其他 token。在 few-shot 场景中，模型可以「看到」所有示例的输入-输出对应关系，注意力权重会自动捕捉这种模式。从数学上看，这相当于在上下文中构建了一个隐式的 条件概率分布：

公式1: Few-shot 的条件概率视角 $$P(y \mid x, \mathcal{D}) = \frac{\exp(f_\theta(x, \mathcal{D})_y)}{\sum_{y'} \exp(f_\theta(x, \mathcal{D})_{y'})}$$
其中 $\mathcal{D} = \{(x_1, y_1), ..., (x_k, y_k)\}$ 是示例集，$f_\theta$ 是参数为 $\theta$ 的 Transformer。与标准监督学习不同的是，这里 $\theta$ 不更新，而是通过在前向传播中将 $\mathcal{D}$ 作为额外的上下文注入，让注意力机制隐式地「学习」了从 $x_i$ 到 $y_i$ 的映射模式。实际上，Dai et al. (2023) 证明 Transformer 的前向传播在数学上等价于对某个隐式线性模型执行一步梯度下降——这解释了为什么更多的示例通常意味着更好的表现。

层面三：指令跟随（Instruction Following）能力

对于 zero-shot，模型依赖的是指令跟随能力——它在指令微调 (Instruction Tuning) 阶段学会了「理解并用自然语言指令指导行为」。这也是为什么经过指令微调的模型（如 ChatGPT、Claude）zero-shot 能力远超原始预训练模型。

实操三原则（G8 教程法）：

1先试 zero-shot，不行再加 few-shot
✅ 预期：简单分类、摘要等高共识任务可直接 zero-shot
⚠️ 常见错误：一上来就写 8 个示例，浪费 token 且可能引入示例偏差
2示例要多样且均衡
✅ 预期：如果你的任务有 3 个类别，每个类别至少给 1 个示例
⚠️ 常见错误：所有示例都来自同一类别，导致模型产生严重标签偏差
3示例格式要严格一致
✅ 预期：所有示例采用完全相同的格式，包括标点符号和换行方式
⚠️ 常见错误：示例之间格式不统一，模型会学到错误格式而非任务逻辑

理解零样本/少样本提示的完整技术架构，需要看清从用户输入到模型输出的端到端流程。以下是核心架构分层：

在少样本模式中，前向传播时 Transformer 的自注意力机制实际上执行了一种 隐式匹配：模型将待推理输入的 attention pattern 与所有示例输入的 attention pattern 进行比较，找到最相似的示例，然后「类比」输出。这可以理解为一种软性的 nearest-neighbor 搜索——只不过搜索是并行地、连续地发生在高维语义空间中。

核心工具算力与成本分析⏱ 约3分钟

同样的任务，zero-shot 只要 50 tokens，few-shot 可能要 800 tokens——成本差 16 倍。在规模化使用时，选择哪种方案直接影响你的预算。

不同提示策略的 token 消耗差异巨大，这直接影响 API 成本和推理延迟：

策略典型 prompt tokensGPT-4o 单次成本千次调用成本延迟

公式2: 单次 API 调用成本估算 $$\text{Cost} = P_{\text{in}} \times C_{\text{input}} + P_{\text{out}} \times C_{\text{output}}$$
其中 $P_{\text{in}}$ 是输入 token 数（包含系统提示 + 用户 prompt + 示例），$P_{\text{out}}$ 是输出 token 数，$C_{\text{input}}$ 和 $C_{\text{output}}$ 是每 token 单价。以 GPT-4o 为例，$C_{\text{input}} = \$2.50/1M$ tokens，$C_{\text{output}} = \$10.00/1M$ tokens。一个典型的 5-shot prompt（~800 input tokens）产出 100 output tokens 的单次成本约为 $0.003。

成本优化建议：

  • 最优示例数：研究发现 4-8 个示例通常是性价比最优区间——超过8个示例后边际收益急剧下降。
  • 缓存策略：如果多个请求共享相同的示例集，使用 prompt caching（如 Anthropic 的 prompt caching）可节省 90% 的示例 token 开销。
  • 动态选择：在生产系统中，先 zero-shot 尝试，置信度低时自动降级为 few-shot。

关键发现：

  • 高共识任务：常识推理（HellaSwag）、简单代码生成中，zero-shot 和 few-shot 差距很小（1-3%）。直接 zero-shot 即可。
  • 复杂推理任务：在 BBH（BIG-Bench Hard）、数学推理（GSM8K）中，few-shot 比 zero-shot 有 3-5% 的稳定提升。投入示例是值得的。
  • 知识密集型任务：MMLU 的 few-shot 增益最小（~2%），说明对于「回忆知识」类的任务，示例的作用有限。
  • 小模型受益更多：对于 7B-13B 级别的模型，few-shot 相比 zero-shot 的提升通常更大（5-15%），因为小模型更需要示例来「锚定」任务。

公式3: 示例数量的边际收益递减模型 $$\Delta \operatorname{Acc}(k) = \operatorname{Acc}(k) - \operatorname{Acc}(0) \approx A \cdot (1 - e^{-k/B})$$
这是一个经验公式，其中 $A$ 是最大可能的提升幅度（任务相关），$B$ 是「半饱和」示例数（通常 2-4）。当 $k = B$ 时收益达到最大值的约 63%。研究表明大多数 NLP 任务的 $B$ 在 2-4 之间，$A$ 在 3-15% 之间。这意味着超过 8 个示例后，每增加一个示例的边际收益通常低于 0.5%。

当前趋势是：推理模型（如 o1、DeepSeek-R1）正在模糊 zero-shot 和 few-shot 的边界——它们通过内部推理链在 zero-shot 模式下就能达到传统 few-shot + CoT 的效果，这可能是下一个重要的范式转变。

场景五：数据增强（Few-shot）

利用 few-shot 生成训练数据是当前最常见的工业应用之一。给定 3-5 个标注样本，让模型生成 100+ 个同分布样本。但需注意：生成的样本可能带有模型自身的偏差。

实践应用实践案例⏱ 约4分钟

一个电商客服团队用 few-shot 将自动分类准确率从 72% 提升到 94%，而成本只增加了 40%。这不是魔法——是正确的示例选择和 prompt 设计的结果。

案例 1：电商客服工单分类系统

背景：某电商平台每天收到 5000+ 客服工单，需要自动分类为「退款」「换货」「物流查询」「投诉」「咨询」五类。

方案演化：

  • V1 (Zero-shot)：准确率 72%。问题：模型对「退款」和「换货」混淆严重（两者都涉及退货流程）。
  • V2 (5-shot)：准确率 94%。关键改进：为每个类别选了 1 个「边界案例」作为示例（如「商品有质量问题，但我不想要了，能退吗？」→ 退款 vs 换货的边界）。

代码实现（DSPy 框架）：

DSPy Few-shot 分类优化 import dspy class TicketClassifier(dspy.Signature): """将客服工单分类为五个类别之一""" ticket = dspy.InputField() category = dspy.OutputField(desc="退款/换货/物流查询/投诉/咨询") classify = dspy.ChainOfThought(TicketClassifier) # 使用 DSPy 自动搜索最优 few-shot 示例 from dspy.teleprompt import BootstrapFewShot optimizer = BootstrapFewShot(metric=accuracy_metric) optimized = optimizer.compile(classify, trainset=train_examples)

成本分析：V1 平均 35 tokens/请求 → $0.00009/次；V2 平均 280 tokens/请求 → $0.0007/次。日均 5000 请求，月成本从 $13.5 增至 $105——但省下的 22% 人工审核成本约 $8000/月。

风险与挑战潜在风险⏱ 约3分钟

Few-shot 不是越多样例越好——选错了示例比不给示例还糟糕。这被称为「示例偏差」，是提示工程中最容易被忽视的陷阱。

零样本/少样本提示在实际应用中的主要风险：

风险类型描述影响程度缓解策略
示例偏差 (Label Bias)示例的标签分布不均导致模型倾向于高频标签🔴 高确保每个类别至少 1 个示例；使用平衡采样
顺序敏感 (Order Sensitivity)改变示例的排列顺序可能导致不同输出🟡 中多次推理取多数票；随机排列示例
格式过拟合 (Format Overfitting)模型学习示例的格式而非任务逻辑🟡 中在测试 prompt 中微调格式以检验鲁棒性
幻觉放大 (Hallucination)Few-shot 示例中的虚构信息被模型「学习」并复制🔴 高严格审查示例内容的真实性；添加「如不确定请标注」指令
上下文窗口溢出过多示例超出模型上下文窗口导致截断🟡 中动态计算 token 数；使用示例选择策略
对抗注入 (Prompt Injection)攻击者在用户输入中嵌入指令，覆盖 zero-shot 任务定义🔴 高使用分隔符隔离用户输入；输入清洗
公式4: 示例顺序敏感度量化 $$\operatorname{OSI} = \frac{\max_{\pi \in S_k} \operatorname{Acc}(\pi) - \min_{\pi \in S_k} \operatorname{Acc}(\pi)}{\operatorname{Acc}_{\text{avg}}}$$
$\operatorname{OSI}$ 衡量示例排列顺序对准确率的影响程度。$S_k$ 是 $k$ 个示例的所有排列，$\operatorname{Acc}(\pi)$ 是排列 $\pi$ 下的准确率。$\operatorname{OSI} \gt 0.15$ 表示顺序敏感度很高，建议使用多次随机排列取均值。Lu et al. (2022) 发现 GPT-3 在部分任务上 $\operatorname{OSI}$ 可达 0.20-0.30。

风险与挑战伦理与安全⏱ 约3分钟

一个看似无害的 few-shot 分类 prompt，可能因为示例中的隐性偏见而系统性歧视某些群体——你写的每个示例都在「训练」模型的价值观。

零样本/少样本提示的伦理问题常常被低估，因为人们容易认为「只是给几个例子而已」。但研究表明，示例对模型输出有直接的价值观塑造效应：

1. 刻板印象传播

如果 few-shot 示例中所有医生都是男性、所有护士都是女性，模型会在后续推理中复现这种刻板印象。Zhao et al. (2021) 的经典实验表明，仅仅改变一个分类示例中的性别代词，就能使模型对职业性别的预测翻转 40% 以上。

2. 文化偏见放大器

示例中的文化默认（如所有示例都用英文名字、西方场景）会让模型在非西方语境下表现显著下降。Hershcovich et al. (2022) 发现，用全英文示例进行 few-shot 分类时，模型对非英语文化场景的准确率下降 15-20%。

3. 越狱风险

Few-shot 示例可以被恶意设计来绕过安全护栏。例如，在 prompt 中给出几个「拒绝回答」的示例，再给一个「但这次破例」的示例，可能诱导模型在后续回答中降低安全标准。

✓伦理审查清单（建议在发布 prompt 前逐一检查）
✅ 示例是否覆盖了不同性别/文化/年龄的角色？
✅ 示例比例是否反映真实分布（而非刻板印象分布）？
✅ 是否添加了明确的安全边界指令？（如「请拒绝回答涉及非法活动的请求」）
⚠️ 不要假设模型会自动纠正你的示例偏见——它们不会。

发展演进发展前景⏱ 约3分钟

当 GPT-5 的 zero-shot 能力已经超过 GPT-4 的 8-shot 时，few-shot 还有存在的意义吗？答案是：有的——但在快速变化。

趋势一：Zero-shot 能力的持续跃升

每一代新模型的 zero-shot 能力都在逼近上一代模型的 few-shot 水平。这主要得益于：(1) 更大规模的预训练数据；(2) 更精细的指令微调；(3) RLHF/DPO 等对齐技术的成熟。预计未来 1-2 年内，简单到中等难度的 NLP 任务将基本实现「zero-shot 即够用」。

趋势二：Few-shot 从「演示」到「校准」

Few-shot 的角色正在从「教模型怎么做」转变为「校准模型的输出分布」。在推理模型（如 o1、DeepSeek-R1）上，few-shot 的主要价值不再是提供任务定义，而是校准输出格式、风格和精度。

趋势三：动态示例选择（Dynamic Example Selection）

与其使用固定的示例集，未来系统将根据每个输入动态选择最相关的示例。这类似于 RAG（检索增强生成）的思路——从示例库中检索与当前输入最相似的 k 个示例组成 prompt。DSPy 和 LangChain 已经提供了这方面的初步工具。

趋势四：自动 prompt 优化

手工编写 few-shot 示例正在被自动化工具取代。DSPy、TextGrad 等框架可以自动搜索最优示例组合和排列，将 prompt 工程从「手艺活」转变为「优化问题」。

核心概念常见误区⏱ 约3分钟

「Zero-shot 就是不给例子，Few-shot 就是给例子」——如果你对两者的理解止步于此，你已经在犯第一个错误了。

误区 1：「Zero-shot = 零信息」

Zero-shot 不是「什么都不给模型」，而是「不给示例但给清晰的指令」。一个精心设计的 zero-shot prompt 可能比一个模糊的 few-shot prompt 效果更好。在实践中，「指令的清晰度」比「是否有示例」更重要。

误区 2：「示例越多效果越好」

这是最常见也最昂贵的误解。如前文公式所示，few-shot 收益服从边际递减规律。超过 8 个示例后，每增加一个示例的准确率提升通常低于 0.5%。盲目堆叠示例不仅浪费 token，还可能引入更多噪声和偏差。

误区 3：「Zero-shot 只适合简单任务」

随着模型能力的提升，zero-shot 在越来越多的复杂任务上表现出色。GPT-4o 的 zero-shot 在 GSM8K 数学题上达到 92%，在 HumanEval 代码生成上达到 90%——这些都不是「简单任务」。真正的限制在于：zero-shot 对指令的质量极其敏感。

误区 4：「Few-shot 可以解决所有问题」

Few-shot 不能创造知识——它只是让模型更好地利用已有的知识。如果任务需要的知识不在模型的预训练数据中，再多的示例也无法弥补。在这种情况下，需要结合 RAG（检索增强生成）或微调。

误区 5：「格式无关紧要」

示例的格式一致性是 few-shot 成功的关键。研究表明，当示例之间格式不一致时，模型的性能可能下降 20-30%。这是因为模型会同时学习格式和任务逻辑，格式的噪声会干扰任务学习。

学习评估总结回顾⏱ 约2分钟

从 GPT-3 的惊人发现到今天的产业标配，零样本与少样本提示走过了一条从实验到实用的道路。让我们回顾一下核心要点。

核心要点回顾：

  1. 范式转变：In-context learning 让 LLM 在不更新参数的情况下完成任务，开启了提示工程时代。
  2. 梯度选择：从 zero-shot（无示例）到 few-shot（2-8 个示例），选择取决于任务复杂度和指令清晰度。
  3. 底层原理：Transformer 的自注意力机制让模型能够在上下文中建立示例与待推理输入之间的关联。
  4. 成本权衡：示例越多准确率可能越高，但 token 成本和延迟也随之增加，边际收益递减。
  5. 关键风险：示例偏差、顺序敏感、格式过拟合是 few-shot 的三大陷阱。
  6. 伦理考量：示例中的隐性偏见会被模型学习和放大，需要进行偏见审计。

下一步行动建议：

  • 用 zero-shot 尝试你当前的任务——可能已经足够好
  • 如果效果不佳，尝试 3-5 个精心选择的示例
  • 测试不同示例顺序的稳定性
  • 监控生产环境中的实际表现，持续迭代
零样本与少样本提示是提示工程的基石。掌握这一技法，你就掌握了与 LLM 对话的基本语言。记住：先试 zero-shot，不行再加 few-shot，永远保持示例的多样性和格式一致性。
