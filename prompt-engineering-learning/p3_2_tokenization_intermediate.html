前置知识背景与缘起⏱ 约3分钟

为什么不直接用词或字符？因为两者各有缺陷——词表太大OOV问题严重，字符序列又太长。

三种分词方案的对比：

方案优点缺点例子
词级别符合直觉，语义单位完整词表巨大，OOV（未登录词）问题严重unhappiness → [unhappiness]
字符级别词表极小，无OOV问题序列太长，语义信息分散unhappiness → [u,n,h,a,p,p,i,n,e,s,s]
子词级别折中方案，兼顾效率与覆盖需要预训练词表，结果不直观unhappiness → [un, happiness]

现代LLM的选择：所有主流模型（GPT、BERT、T5等）都使用子词级别的token化方案。

核心概念核心概念⏱ 约4分钟

Token是LLM的"原子"——每个token对应词表中的一个id，模型通过预测下一个token的概率分布来生成文本。
图：文本→Token→ID的转换过程

Token的本质：

Token可以是：

  • 完整的单词（如 "hello"）
  • 单词的一部分（如 "un-"、"-ing"）
  • 单个字符（如 "a"、"好"）
  • 特殊标记（如 [CLS]、[SEP]、<|endoftext|>）

经验法则（估算token数）：

  • 英文：约 1 token = 0.75 个单词
  • 中文：约 1 token = 1.5 个汉字
  • 代码：约 1 token = 1 个字符
💡 提示工程启示： 中文字符的token效率比英文低——相同长度的prompt，中文能承载的信息更少。使用英文提示词有时能获得更好的性价比。

核心原理Byte-Pair Encoding⏱ 约6分钟

BPE是GPT系列使用的token化算法。核心思想：从字符开始，不断合并最常见的字符对。

BPE算法步骤：

1初始词表：所有单个字符
例如：[a, b, c, d, ..., z]
2统计频率：统计训练语料中所有相邻字符对的出现频率
找出最常见的组合（如 "e"+"r"）
3合并：将频率最高的字符对合并为一个新token
加入词表：[a, b, ..., z, er]
4重复：重复步骤2-3，直到词表达到预设大小
GPT-2：50,257个token；GPT-3：~50k；GPT-4：~100k
BPE算法的简化实现 def bpe_train(text, vocab_size): # 初始词表：所有字符 vocab = set(text) while len(vocab) < vocab_size: # 统计字符对频率 pairs = {} for i in range(len(text)-1): pair = (text[i], text[i+1]) pairs[pair] = pairs.get(pair, 0) + 1 # 找出最常见的字符对 most_common = max(pairs, key=pairs.get) # 合并 merged = most_common[0] + most_common[1] vocab.add(merged) # 更新文本 new_text = [] i = 0 while i < len(text): if i < len(text)-1 and (text[i], text[i+1]) == most_common: new_text.append(merged) i += 2 else: new_text.append(text[i]) i += 1 text = new_text return vocab
💡 关键洞察： BPE不是基于语言学规则，而是纯数据驱动——它找出的是训练语料中最常一起出现的字符序列。这解释了为什么某些词会被奇怪地切分。

核心原理WordPiece & SentencePiece⏱ 约5分钟

BPE不是唯一选择——不同模型使用不同的token化算法，理解差异能帮你写出更好的提示。
算法使用模型核心思想特点
BPEGPT系列、LLaMA合并最常见的字符对简单高效，纯频率驱动
WordPieceBERT、T5、PaLM最大化语言模型概率考虑语言模型，更智能
SentencePieceT5、LLaMA、多语言模型将空格视为普通字符无空格特殊处理，多语言友好
UnigramT5、ALBERT从大词表开始逐步删除概率建模，更灵活

空格处理的差异（重要！）：

不同算法对空格的处理 # GPT (BPE)：空格+词作为一个token "hello world" → [hello, Ġworld] # Ġ表示空格 # BERT (WordPiece)：词前加##表示子词 "unhappiness" → [un, ##happiness] # SentencePiece：空格是_ "hello world" → [hello, _world]
💡 提示工程启示： 不同模型的token化方式不同——同一个prompt在不同模型上的token序列可能不同。在微调或跨模型使用时，这一点尤为重要。

实践应用编码/解码流程⏱ 约5分钟

实际使用tokenizer：文本→token→ID→模型→ID→token→文本。这是一个双向的过程。
使用HuggingFace Tokenizers from transformers import GPT2Tokenizer, BertTokenizer # GPT-2 tokenizer tokenizer = GPT2Tokenizer.from_pretrained("gpt2") text = "Hello, how are you?" tokens = tokenizer.tokenize(text) print("Tokens:", tokens) # ['Hello', ',', 'how', 'are', 'you', '?'] ids = tokenizer.encode(text) print("IDs:", ids) # [15496, 11, 703, 389, 345, 30] decoded = tokenizer.decode(ids) print("Decoded:", decoded) # "Hello, how are you?" # BERT tokenizer bert_tokenizer = BertTokenizer.from_pretrained("bert-base-uncased") bert_tokens = bert_tokenizer.tokenize(text) print("BERT tokens:", bert_tokens) # ['hello', ',', 'how', 'are', 'you', '?']

核心原理Token边界效应⏱ 约5分钟

Token边界不是任意的——它会影响模型的理解和生成。好的提示词应该考虑token结构。

现象1：截断在token中间

坏的截断 vs 好的截断 # 坏：截断在token中间 "我是一个很长的句子，需要被截..." → 最后一个token不完整 # 好：在完整token边界截断 "我是一个很长的句子，需要被" → 所有token完整

现象2：某些词更容易被生成

因为词表中某些词是单个token，而另一些是多个token——模型倾向于生成更"便宜"（token数少）的表达方式。

图：不同表达的token成本对比

现象3：空格的重要性

在GPT系列中，空格+词通常是一个单独的token——缺少空格可能会改变token序列。

💡 提示工程技巧： 1. 重要内容不要放在可能被截断的位置；2. 使用更常见的、单个token的表达方式；3. 注意空格的使用，保持一致性。

实践应用实践案例⏱ 约5分钟

一个真实的案例：通过调整提示的token结构，大幅提升了输出质量。
案例：控制JSON输出格式 # 初始提示（token效率低） prompt = """请输出一个JSON，包含name和age字段： { "name": "张三", "age": 25 }""" # 优化后的提示（考虑token结构） prompt = """Output JSON with "name" and "age": {"name":"张三","age":25}""" # 空格更少，token更紧凑

结果：优化后的提示输出有效JSON的概率提升了约15%。原因：

  • 更紧凑的格式减少了token数量
  • 避免了空格带来的token边界问题
  • 示例本身就是一个完整的token序列
💡 经验： 对于需要精确格式的任务（如JSON、代码），在示例中使用紧凑格式通常能获得更好的结果——因为token序列更接近训练数据中的代码/数据格式。
