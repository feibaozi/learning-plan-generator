基础背景

背景与缘起

当一条SQL不够用时——子查询如何成为SQL的"乐高积木"？

子查询（Subquery）的概念几乎与SQL语言本身同时诞生。早在1970年代System R项目期间，研究人员就意识到：复杂的数据分析需求往往无法用单层SELECT语句表达。你需要先算一个中间结果，然后基于这个中间结果再查——这就是子查询的核心思想。

子查询本质上是一个嵌套在另一个SQL语句中的SELECT语句。它可以出现在SELECT子句（标量子查询）、FROM子句（派生表）、WHERE子句（条件子查询）甚至HAVING子句中。这种"查询套查询"的模式让SQL获得了分步、分层处理数据的能力。

然而随着查询复杂度增加，多层嵌套的子查询变得难以阅读和维护。1999年，SQL:1999标准引入了CTE（Common Table Expression，通用表表达式），通过WITH关键字将子查询从"inline"提到"predefined"位置，大幅提升了复杂查询的可读性。2005年SQL Server率先实现递归CTE，PostgreSQL 8.4和MySQL 8.0随后跟进。

今天的CTE不仅是可读性工具——它还是递归查询的唯一方式（在标准SQL中），是现代数据仓库SQL的标配语法。

核心要点：

子查询是SQL的"嵌套思维"，CTE是"解嵌套"的革命性语法。从子查询到CTE的演进，本质是从"写完即忘"到"命名复用、逐层构建"的编程思维提升。

核心概念

核心概念

标量子查询、多行子查询、关联子查询——三种子查询形态，三种完全不同的执行方式

标量子查询（Scalar Subquery）

返回单行单列值，可以放在SELECT、WHERE、SET等任何期望单一值的位置。例如：SELECT name, (SELECT AVG(salary) FROM employees) AS avg_company FROM employees;——每行都附带一个全公司平均薪资。

多行子查询

返回多行结果，配合IN / EXISTS / ANY / ALL操作符使用。IN是"属于这个集合"，EXISTS是"存在匹配行"（找到即停，效率高于IN）。

关联子查询（Correlated Subquery）

子查询内部引用了外部查询的列，导致子查询对外部每一行都要执行一次。这是最容易被误用的子查询类型——性能可能极差。典型写法：

SELECT e.name, e.salary FROM employees e
WHERE e.salary > (SELECT AVG(salary) FROM employees WHERE dept_id = e.dept_id);

CTE（通用表表达式）

CTE通过WITH子句将一个子查询命名并前置，后续查询可以像引用普通表一样引用它。分为两种：

  • 非递归CTE：普通的"WITH name AS (SELECT ...)"，提升可读性，MySQL 8.0中物化执行
  • 递归CTE：WITH RECURSIVE，用于处理树形/层级数据（组织架构、分类树、BOM清单）
图：子查询与CTE的层级关系
核心要点：

子查询按返回结果分为标量（单值）、多行（集合）、关联（依赖外部）。CTE是子查询的"命名升级版"，将"写在里面的"变成"写在前面的"，让复杂查询像搭积木一样逐层构建。

核心原理

核心原理

优化器是如何处理子查询的？——从子查询展开到半连接转换的幕后机制

数据库优化器处理子查询的方式直接影响查询性能。以下是关键优化策略：

1. 子查询展开（Subquery Unnesting）

优化器将IN/EXISTS子查询转换为半连接（Semi-Join）或反半连接（Anti-Semi-Join）。例如：

-- 原始查询
SELECT * FROM orders WHERE user_id IN (SELECT id FROM users WHERE city='北京');

-- 优化器等价变换为
SELECT o.* FROM orders o
SEMI JOIN users u ON o.user_id = u.id AND u.city = '北京';

Semi-Join：B表中有匹配行则A表行保留，且B表匹配行不输出到结果（与INNER JOIN的区别）。这样可以避免重复行问题。

2. 派生表合并（Derived Table Merge）

FROM子句中的子查询（派生表）会被优化器尝试合并到外层查询中，避免物化子查询结果。

3. CTE物化策略

MySQL 8.0默认将CTE物化（materialize）——即先执行一次CTE查询，将结果存入临时表，后续引用直接读临时表。多次引用同一个CTE时，物化避免了重复计算。但如果CTE只引用一次，物化的开销可能高于合并。

4. 递归CTE的工作原理

递归CTE分为两部分：

WITH RECURSIVE cte AS (
  SELECT ... WHERE ...        -- 锚点成员（Anchor Member）：初始数据
  UNION ALL
  SELECT ... FROM cte WHERE ... -- 递归成员（Recursive Member）：基于上一步结果
)
SELECT * FROM cte;

执行过程：锚点→结果1→基于结果1的递归→结果2→基于结果2的递归→...→直到递归成员返回0行。

核心要点：

子查询优化的核心机制：IN→Semi-Join、派生表→合并、CTE→物化。理解这些转换是写出高性能子查询的前提——知道优化器会怎么处理你的查询。

执行架构

CTE执行架构

从CTE声明到最终结果：深入了解CTE在MySQL/PostgreSQL中的完整执行路径

CTE的执行分为以下阶段：

  1. 解析：将WITH子句解析为独立的查询树节点，建立CTE名称到子查询的映射
  2. 引用解析：将后续查询中对CTE名称的引用替换为对应的子查询树
  3. 物化决策：优化器根据CTE被引用的次数决定物化策略——引用≥2次通常物化，1次则可能合并到主查询
  4. 执行：若物化，先执行CTE并将结果写入临时表；若合并，则将CTE查询树融入主查询的执行计划

多CTE的执行可以视为流水线——CTE1→CTE2→主查询，每个CTE的输出作为下级的输入。

图：多CTE流水线执行流程
核心要点：

CTE物化策略取决于引用次数。多次引用=物化（空间换时间），单次引用=合并（避免物化开销）。这在生产环境调优时需要重点关注。

实践应用

实践应用

子查询和CTE在工作中怎么用？——四大经典场景全覆盖

场景1：排除特定数据（NOT IN / NOT EXISTS）

-- 找出从未下过单的用户
SELECT * FROM users
WHERE id NOT IN (SELECT DISTINCT user_id FROM orders);

场景2：多步骤数据清洗（CTE链式处理）

WITH clean_orders AS (
  SELECT * FROM orders WHERE status != 'cancelled'
), user_totals AS (
  SELECT user_id, SUM(amount) AS total_spent
  FROM clean_orders GROUP BY user_id
)
SELECT u.name, COALESCE(t.total_spent, 0) AS total
FROM users u LEFT JOIN user_totals t ON u.id = t.user_id;

场景3：组织架构（递归CTE）

WITH RECURSIVE org_tree AS (
  SELECT id, name, manager_id, 1 AS level
  FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, t.level + 1
  FROM employees e JOIN org_tree t ON e.manager_id = t.id
) SELECT * FROM org_tree ORDER BY level, name;

场景4：行级比较（关联子查询）

-- 找出薪资高于本部门平均的员工
SELECT e.name, e.salary, e.dept_id FROM employees e
WHERE e.salary > (SELECT AVG(salary) FROM employees WHERE dept_id = e.dept_id);
核心要点：

子查询的四大工作场景：排除（NOT IN/EXISTS）、链式清洗（多CTE）、层级递归、行级比较（关联子查询）。CTE尤其适合"多步骤数据加工"类分析需求。

实践案例

实践案例

用户留存分析：用CTE一步步拆解这个经典的数据分析需求

需求：电商平台需要计算新用户7日留存率。即：在某周注册的用户中，有多少人在注册后7天内产生了订单。

WITH new_users AS (
  SELECT id, name, register_date FROM users
  WHERE register_date BETWEEN '2026-03-01' AND '2026-03-07'
), user_orders AS (
  SELECT DISTINCT o.user_id FROM orders o
  INNER JOIN new_users nu ON o.user_id = nu.id
  WHERE o.order_date BETWEEN nu.register_date AND DATE_ADD(nu.register_date, INTERVAL 7 DAY)
)
SELECT nu.register_date,
  COUNT(DISTINCT nu.id) AS total_new,
  COUNT(DISTINCT uo.user_id) AS retained,
  ROUND(COUNT(DISTINCT uo.user_id) * 100.0 / COUNT(DISTINCT nu.id), 2) AS retention_rate
FROM new_users nu
LEFT JOIN user_orders uo ON nu.id = uo.user_id
GROUP BY nu.register_date
ORDER BY nu.register_date;
图：每日新用户7日留存率趋势

为什么用CTE而不是子查询？这里定义了两个中间结果集——new_users和user_orders——每一步都是独立的业务概念。用CTE写，每个步骤可独立测试：先跑CTE1确认日期范围，再跑CTE2检查是否有重复的user_id。

核心要点：

CTE的核心优势不是性能（物化可能比合并慢），而是可维护性——每一步都是一个可独立测试和理解的业务单元。复杂分析就应该用CTE拆解。

风险与陷阱

潜在风险

一个关联子查询跑5分钟——你写的子查询可能比你想象的慢1000倍

🔴 致命陷阱：关联子查询的N+1问题

外层表有N行时，关联子查询执行N次——外层50万行就执行50万次子查询。注意NOT IN + NULL的隐蔽问题：如果子查询结果中包含NULL，NOT IN永远返回空。

🟠 IN vs EXISTS 选择不当

一般原则：外层表大用EXISTS（找到即停），子查询结果集大且无索引用EXISTS（避免全表扫描后去重）。但现代优化器通常会自动转换，差异变小。

CTE过度物化

CTE只被引用一次时，物化策略反而增加I/O。PostgreSQL 12+默认不再强制物化CTE（MATERIALIZED / NOT MATERIALIZED可控制）。

核心要点：

关联子查询是性能杀手，动手前先评估外层表行数。NOT IN + NULL = 永远空集。CTE物化策略在MySQL中不可控（强制物化），在PostgreSQL中可显式声明。

常见问题

常见问题诊断

子查询结果不对？CTE跑了很久？递归停不下来？——排查指南

问题1：子查询返回多于一行报错

标量子查询只允许返回一行。当WHERE条件过滤不够精确时发生此错误。解决：加LIMIT 1或改用IN/EXISTS。

问题2：递归CTE无限循环

如果在父子关系中存在环（A→B→C→A），递归CTE会无限执行直到达到深度限制。解决：用数组记录访问路径，每次递归前检查是否已访问过。

问题3：派生表性能差

FROM子查询如果包含GROUP BY/排序等操作，EXPLAIN中可能显示"Using temporary; Using filesort"。解决：尝试将派生表改写为CTE或以JOIN替代。

核心要点：

标量子查询报错→加LIMIT 1，递归死循环→记录访问路径，派生表慢→看EXPLAIN中是否有temp/filesort。

未来趋势

发展趋势

从CTE到Pipelined CTE：下一代子查询技术正在改变数据处理的范式

  • Pipelined CTE：DuckDB等现代数据库实现CTE流水线执行——CTE之间的数据以流式传递，不落盘不物化，性能远超传统物化模式。
  • 增量CTE（Incremental CTE）：Materialize等流式数据库支持对CTE的增量维护——源表更新时CTE结果自动刷新。
  • CTE as Views：Snowflake/BigQuery支持将CTE临时结果注册为会话级视图，跨多个查询复用。
核心要点：

CTE的未来是"流水线化"和"增量化"——从一次性物化到流式处理，从查询时计算到实时维护。DuckDB的Pipelined CTE代表了性能最优解。

学习指导

学习建议

  1. 从子查询到CTE的渐进路线：先掌握标量和IN子查询→关联子查询→派生表→非递归CTE→递归CTE
  2. 练习改写：找3条已有的嵌套子查询SQL，将其改写为CTE版本，对比可读性和EXPLAIN输出
  3. 理解优化器：使用EXPLAIN FORMAT=TREE查看优化器如何处理子查询（是否展开为Semi-Join、派生表是否合并）
  4. 递归CTE专项练习：在测试库创建组织架构表，练习找下属、找上级、找所有祖先节点的递归查询
核心要点：

子查询→CTE→递归CTE是循序渐进的能力阶梯。改写已有查询+EXPLAIN验证是最高效的学习方式。

认知纠偏

常见误区

  • "CTE一定比子查询快"：错。MySQL中CTE强制物化，如果只引用一次且外层有WHERE过滤，物化的全量结果可能比内联派生表慢。
  • "EXISTS一定比IN快"：在现代优化器中，IN通常会自动转换为Semi-Join，与EXISTS性能差异很小。
  • "子查询必须用括号"：标准SQL中子查询需要括号，但CTE不需要外层括号——这是CTE的语法优势之一。
  • "递归CTE可以替代所有循环"：递归CTE有深度限制，且中间结果无法修改。复杂的迭代逻辑（如循环中累加不同值）更适合用存储过程。
核心要点：

CTE不总是更快，EXISTS不总是优于IN。关键看实际执行计划和数据库版本。以EXPLAIN为准，不要盲信经验法则。

争议与讨论

子查询 vs CTE vs 临时表 vs 视图——哪种才是最佳实践？

子查询派：简单场景下子查询最直接，优化器有成熟的转换路径。小查询没必要引入CTE的额外语法噪音。

CTE派：任何涉及多个中间步骤的查询都应该用CTE。可读性优先，让后续维护者（包括3个月后的你自己）能看懂。

临时表派：对于中间结果需要被多次引用且数据量大的场景，CREATE TEMPORARY TABLE + 建索引比CTE物化更可控。

业界共识：遵循"复杂度驱动选择"原则——1层嵌套用子查询，2-3层用CTE，多次引用+大数据量用临时表。没有万能方案，只有合适选择。

核心要点：

子查询/CTE/临时表各有适用场景。简单→子查询，层级多→CTE，重复引用量大→临时表。关键是以维护者的视角来选择，而非只看当前写代码的便利。
