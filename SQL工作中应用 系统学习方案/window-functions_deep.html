基础背景

背景与缘起

GROUP BY把明细数据聚合得面目全非——窗口函数的出现，让"既不丢失明细行，又能做跨行计算"的梦想成真

在窗口函数出现之前，SQL有一个根本性的矛盾：分组聚合（GROUP BY）会压扁明细数据，但业务分析经常需要在保留每行详情的同时计算同组统计量。比如"每行显示员工薪资+本部门平均薪资"——用标准聚合做不到这一点。

这个困境的解决方案是窗口函数（Window Function）。它于2003年首次出现在SQL:2003标准中，由数据库理论家Jim Melton等人推动。核心理念：定义一个"窗口"（一组行的集合），对窗口内每行独立计算函数值，不减少行数、不破坏原有行顺序。

PostgreSQL 8.4（2009）率先实现，Oracle和SQL Server随后，MySQL是最晚的一个——直到8.0（2018）才正式支持。今天窗口函数已成为数据分析师和BI工程师的必备技能，在排名、同比环比、移动平均、累计求和等场景中无处不在。

核心要点：

窗口函数的本质是"在不改变结果集行数前提下，对每一行计算基于其窗口范围的值"。它解决了聚合函数丢失行级细节的痛点，是SQL分析能力的质变。

核心概念

核心概念

ROW_NUMBER排序，RANK处理并列，LAG看上一行——窗口函数家族速览

窗口函数可以分为三大类：

1. 排名函数（Ranking Functions）

函数行为并列处理
ROW_NUMBER()分配唯一连续序号（1,2,3,4...）无并列，随机决定顺序
RANK()排名，并列占位（1,2,2,4...）并列跳过后续序号
DENSE_RANK()排名，并列不占位（1,2,2,3...）并列不跳过序号
NTILE(N)将数据均分为N个桶分配桶号1~N

2. 偏移函数（Offset Functions）

LAG(expr, offset, default)：获取前offset行的值，用于环比计算。LEAD(expr, offset, default)：获取后offset行的值。它们让你无需自连接就能访问相邻行。

SELECT date, revenue,
  LAG(revenue, 1) OVER (ORDER BY date) AS prev_day_rev,
  revenue - LAG(revenue, 1) OVER (ORDER BY date) AS change
FROM daily_sales;

3. 聚合窗口函数

SUM/AVG/COUNT/MIN/MAX都可以配备OVER子句变成窗口函数。与标准聚合的区别：不压缩行。

图：窗口函数分类与关系
核心要点：

排名函数（ROW_NUMBER/RANK/DENSE_RANK/NTILE）、偏移函数（LAG/LEAD）、聚合窗口函数（SUM OVER等）构成了窗口函数的三大支柱。

核心原理

核心原理

PARTITION BY分窗口，ORDER BY定顺序，ROWS/RANGE画边界——窗口函数的三要素

窗口函数的完整语法：

窗口函数语法结构
$$FUNC(expr)\ \text{OVER}\ ([\text{PARTITION BY}\ col]\ [\text{ORDER BY}\ col]\ [\text{ROWS/RANGE frame}])$$
三要素解析：
1. PARTITION BY：将数据划分为互不重叠的分组（窗口分区），每个分区独立计算
2. ORDER BY：定义分区内行的排序顺序，是偏移函数和累计聚合的基础
3. 窗口帧（Window Frame）：定义当前行"能看见"的行范围（ROWS按物理行号，RANGE按值范围）

窗口帧详解

窗口帧定义了"窗口中的窗口"——从整个分区中划出一段范围作为当前行的计算域：

  • ROWS BETWEEN 6 PRECEDING AND CURRENT ROW：当前行+前6行（共7行，移动平均常用）
  • ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW：分区首行到当前行（累计求和）
  • RANGE BETWEEN INTERVAL '7' DAY PRECEDING AND CURRENT ROW：日期范围内的行

ROWS vs RANGE的关键区别：ROWS按物理位置计数（第1行、第2行...），RANGE按排序键的值计数。当ORDER BY列有重复值时，ROWS和RANGE的行为截然不同。

SQL逻辑执行顺序中的窗口函数

窗口函数在WHERE、GROUP BY、HAVING之后，ORDER BY之前执行。这意味着不能在WHERE中直接引用窗口函数的结果，必须用子查询或CTE包裹。

核心要点：

窗口函数=PARTITION BY（分窗）+ ORDER BY（排序）+ 窗口帧（范围）。ROWS按物理行、RANGE按值。窗口函数在WHERE后执行，不能直接在WHERE中引用——这是最常见的语法坑。

窗口帧

窗口帧模型

理解窗口帧就是理解窗口函数——三种帧模式的直观对比

窗口帧定义了"当前行能看到哪些行"，以下是三种典型帧模式的对比：

模式帧定义典型用途示例
累计模式UNBOUNDED PRECEDING ~ CURRENT ROW累计求和/计数monthly cumulative revenue
滑动窗口N PRECEDING ~ CURRENT ROW移动平均7日移动平均股价
完整分区UNBOUNDED PRECEDING ~ UNBOUNDED FOLLOWING分区内整体统计占总比/全组平均
图：三种窗口帧模式的滑动示意
核心要点：

窗口帧=当前行的视界。UNBOUNDED PRECEDING→累计，N PRECEDING→滑动窗口，完整分区→分组统计。默认帧是RANGE UNBOUNDED PRECEDING~CURRENT ROW。

发展迭代

MySQL 8.0的窗口函数实现使用了Filesort和临时表，而PostgreSQL通过索引扫描可避免额外排序。在大数据量下，两者的性能差距可达数倍。

核心要点：

MySQL 8.0才支持窗口函数（晚于PG近10年），且性能实现依赖filesort。生产环境大数据量窗口查询建议优先用PostgreSQL。

实践应用

实践应用

排名、同比环比、移动平均、累计占比——窗口函数实战四连击

场景1：部门内薪资排名

SELECT name, department, salary,
  RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dept_rank
FROM employees;

场景2：月度环比增长

SELECT month, revenue,
  LAG(revenue, 1) OVER (ORDER BY month) AS prev_month,
  ROUND((revenue - LAG(revenue,1) OVER (ORDER BY month)) * 100.0 / LAG(revenue,1) OVER (ORDER BY month), 2) AS growth_pct
FROM monthly_revenue;

场景3：7日移动平均

SELECT date, price,
  AVG(price) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma_7d
FROM stock_prices;

场景4：累计销售占比

SELECT product, sales,
  SUM(sales) OVER (ORDER BY sales DESC) AS cumulative,
  ROUND(SUM(sales) OVER (ORDER BY sales DESC) * 100.0 / SUM(sales) OVER (), 2) AS cumulative_pct
FROM product_sales;
核心要点：

窗口函数的四大核心场景：分组排名（ROW_NUMBER/RANK）、环比（LAG）、滑动窗口（ROWS N PRECEDING）、累计占比（UNBOUNDED PRECEDING）。

实践案例

实践案例

行转列、Top-N-per-group、去重保留最新——三个真实工作中使用窗口函数解决的高级问题

案例1：每个用户取最新一条记录

WITH ranked AS (
  SELECT *,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
  FROM user_actions
)
SELECT * FROM ranked WHERE rn = 1;

这比 SELECT DISTINCT ON (user_id)...ORDER BY created_at DESC（PG特有语法）更具跨数据库通用性。

案例2：连续登录天数计算

WITH date_diffs AS (
  SELECT user_id, login_date,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) -
    DATEDIFF(login_date, '2020-01-01') AS grp
  FROM user_logins
  GROUP BY user_id, login_date
)
SELECT user_id,
  COUNT(*) AS consecutive_days
FROM date_diffs GROUP BY user_id, grp
ORDER BY consecutive_days DESC;

这里利用了一个巧妙数学性质：连续日期序列中，row_number - 日期偏移恒为常数。

图：用户连续登录天数分布
核心要点：

窗口函数+ROW_NUMBER的组合在去重保留最新、连续值分组等高级场景中极为强大。核心技巧：row_number与值的差值构造分组标识。

风险与陷阱

潜在风险

🔴 致命陷阱

  • WHERE中引用窗口函数：窗口函数在WHERE后执行，直接引用会语法报错。必须用子查询/CTE包裹。
  • 窗口帧误用导致错误结果：默认帧是RANGE UNBOUNDED PRECEDING~CURRENT ROW。忘记显式指定但需要全分区统计时（如占比计算），结果会错。

🟠 性能陷阱

  • 大的PARTITION BY列无索引+ORDER BY列无索引 → 全数据排序（文件排序）→ O(N log N)瓶颈
  • 过多的窗口函数同表引用 → 多次扫描或多次排序
核心要点：

WHERE中引用窗口函数=语法错误，PARTITION BY无索引+大数据=filesort地狱。写窗口函数前先确认WHERE条件已用子查询包裹，排列键上有索引。

常见问题

常见问题诊断

问题1：PARTITION BY后ORDER BY结果不对

检查ORDER BY列是否在PARTITION BY列之前被"分组语义"覆盖——PARTITION BY定义了数据如何被切开，ORDER BY只控制切开后的局部排序。

问题2：多个窗口函数查询极慢

多个窗口函数如果有相同的PARTITION BY+ORDER BY，可用WINDOW子句命名复用：WINDOW w AS (PARTITION BY dept ORDER BY salary)

问题3：ROW_NUMBER实际结果"不稳定"

ROW_NUMBER在ORDER BY有并列值时结果不确定——不同执行可能返回不同顺序。需要确定性结果时加第二个排序列或改用RANK。

核心要点：

PARTITION BY切数据，ORDER BY定义局部序。同规范多窗口函数用WINDOW子句复用。ROW_NUMBER的不确定性在并列时要通过加列或换函数解决。

未来趋势

发展趋势

  • 增量窗口函数：流处理引擎（如Flink SQL）已支持对无界数据流的窗口操作，未来实时窗口计算将成为标准能力。
  • QUALIFY子句：部分数据库（Snowflake/Teradata/DuckDB）支持QUALIFY直接过滤窗口函数结果，避免子查询包裹。SQL标准正在讨论纳入。
  • 向量化窗口执行：DuckDB/ClickHouse对窗口函数实现了向量化批处理，1亿行RANK操作可在秒级完成。
核心要点：

窗口函数的未来：实时流窗口、QUALIFY语法简化、向量化极速执行。关注DuckDB在窗口函数性能上的突破性进展。

学习指导

学习建议

  1. 先理解GROUP BY的局限：在已有数据上尝试用GROUP BY做排名/环比/累计——体验痛苦，才能体会窗口函数的价值
  2. 从ROW_NUMBER入手：这是最直观的窗口函数，掌握后自然理解PARTITION BY和ORDER BY的语义
  3. 练习"等价改写"：将以前用自连接+子查询实现的复杂逻辑用窗口函数重写，对比代码量和性能
  4. 用EXPLAIN验证：观察窗口函数在MySQL中的filesort和在PG中的index scan，直观理解性能差异
核心要点：

窗口函数学习路线：GROUP BY局限→ROW_NUMBER→LAG/LEAD→聚合窗口→窗口帧。改写旧代码是最佳练习方式。

认知纠偏

常见误区

  • "窗口函数就是高级聚合"：窗口函数和聚合的真实区别不在"高级/低级"，而在是否压缩行数。
  • "PARTITION BY和GROUP BY一样"：GROUP BY产生一个输出行/组，PARTITION BY保留所有输入行，每行独立计算。
  • "窗口函数一定比自连接快"：小数据量下自连接可能更快——自连接可用索引而窗口函数必须排序。EXPLAIN后才能下结论。
  • "MySQL 8.0窗口函数很好用"：MySQL的实现依赖filesort+临时表，大数据量下性能远不如PG。这是语法兼容但不等于性能兼容。
核心要点：

窗口≠高级聚合，PARTITION BY≠GROUP BY，窗口函数不一定最快。MySQL的窗口函数实现是语法达标但性能堪忧。

观点碰撞

争议与讨论

窗口函数应该写进SQL标准，还是留给应用层处理？

标准派：窗口函数是SQL强大分析能力的体现，应该在数据库中直接计算，减少网络传输的数据量。数据库引擎能高效利用排序和索引。

应用派：复杂窗口逻辑（尤其是多层嵌套PARTITION BY+多个窗口帧）让SQL难以维护和测试。更倾向于将明细数据拉到Pandas/Spark里面做分析。

业界实践：简单窗口逻辑（排名/环比）放在SQL中；多步骤复杂分析用CTE+窗口函数组合；需要交互式探索的交给分析工具层。LAG的环比计算是窗口函数最不可替代的场景。

核心要点：

窗口函数vs应用层分析：简单场景放SQL，多步骤逻辑用CTE+窗口组合，探索性分析用工具层。关键是选择最适合当前团队能力的方案。
