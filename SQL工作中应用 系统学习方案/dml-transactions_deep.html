基础背景

背景与缘起

查询只是"看"数据——当你的SQL需要"改"数据时，世界就复杂了不止一个维度

SQL的DML（Data Manipulation Language，数据操作语言）——即INSERT、UPDATE、DELETE——在几乎所有数据库课程中都被当作"基础语法"一笔带过。但真实工作场景中，DML才是数据生产系统的核心。查询错了可以重来，删除错了可能无法恢复。

事务（Transaction）的概念在1970年代随关系型数据库同时诞生，由数据库理论先驱Jim Gray在其开创性工作中系统化。事务解决了一个根本问题：一组相关联的数据变更要么全部成功，要么全部失败——不可能出现"转账扣了钱但没到账"这种情况。

ACID（Atomicity/Consistency/Isolation/Durability）是事务的核心原则，1983年由Haerder和Reuter正式命名。今天90%的企业级数据系统仍然依赖事务保证——从银行的转账操作到电商的库存扣减。

核心要点：

DML（增删改）+事务=数据变更的安全网。查询处理"读"，DML+事务处理"写"——写操作涉及的一致性、并发、回滚问题远比读操作复杂。

核心概念

核心概念

INSERT/UPDATE/DELETE是表亲，但每种操作都有自己独特的"坑"

INSERT — 插入数据

-- 标准插入
INSERT INTO users (name, email) VALUES ('张三', 'zhang@example.com');

-- 批量插入（比逐行快10-100倍）
INSERT INTO users (name, email) VALUES
  ('张三','z@e.com'), ('李四','l@e.com'), ('王五','w@e.com');

-- 从查询结果插入
INSERT INTO active_users SELECT * FROM users WHERE status='active';

UPDATE — 更新数据

-- 标准更新（⚠️ 永远带WHERE！）
UPDATE users SET status='vip' WHERE total_spent > 10000;

-- 结合子查询更新
UPDATE products p SET price = (
  SELECT AVG(price) FROM competitors WHERE product_id = p.id
);

DELETE — 删除数据

-- 条件删除（⚠️ 永远带WHERE！）
DELETE FROM temp_logs WHERE created_at < '2025-01-01';

-- 安全删除：先SELECT确认，再DELETE
SELECT COUNT(*) FROM logs WHERE created_at < '2025-01-01'; -- 先看删除量
DELETE FROM logs WHERE created_at < '2025-01-01' LIMIT 1000; -- 分批删除

事务控制语句

START TRANSACTION;
  UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
  UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
COMMIT; -- 或 ROLLBACK 撤销
核心要点：

INSERT/UPDATE/DELETE的黄金法则：UPDATE和DELETE永远带WHERE条件。批量操作分批执行（每次1000-10000行），避免长事务锁表。

核心原理

核心原理

ACID不只是四个字母——它是数据库区别于文件系统的最本质特征

ACID 四原则
$$\text{ACID} = \{A(\text{原子性}),\ C(\text{一致性}),\ I(\text{隔离性}),\ D(\text{持久性})\}$$
逐项解析：
A - 原子性(Atomicity)：事务是不可分割的最小单位，全部成功或全部失败。通过Undo Log实现——修改前先写undo日志，回滚时从undo恢复。
C - 一致性(Consistency)：事务从一种一致状态转到另一种一致状态。约束（主键、外键、CHECK）保证这一点。
I - 隔离性(Isolation)：并发事务之间不可见对方的中间状态。通过锁机制和MVCC实现。
D - 持久性(Durability)：事务提交后，更改永久保存。通过Redo Log实现——先写日志(WAL)再写磁盘。

MVCC：多版本并发控制

MySQL(InnoDB)和PostgreSQL的核心并发机制。原理：每条数据保留多个版本——写操作创建新版本，读操作读取适当的旧版本。这实现了"读不阻塞写，写不阻塞读"。InnoDB通过undo log维护历史版本，PG通过元组可见性。

四种隔离级别

隔离级别脏读不可重复读幻读性能
READ UNCOMMITTED✅ 可能✅ 可能✅ 可能最快
READ COMMITTED❌✅ 可能✅ 可能快
REPEATABLE READ❌❌⚠️ MySQL防/PG可能中等
SERIALIZABLE❌❌❌最慢

MySQL默认REPEATABLE READ，PostgreSQL默认READ COMMITTED。生产环境中，90%的场景READ COMMITTED够用。

核心要点：

ACID是事务的四大保障：A靠Undo Log、C靠约束、I靠MVCC和锁、D靠Redo Log(WAL)。MVCC是最优雅的并发方案——读不阻塞写，写不阻塞读。

执行架构

事务执行架构

从START TRANSACTION到COMMIT：一条写操作在数据库内部的完整旅程

以InnoDB为例，一个UPDATE事务的完整内部执行流程：

  1. 查询目标行：通过索引找到数据页，加载到Buffer Pool
  2. 写Undo Log：记录修改前的旧值到undo日志（为回滚和MVCC使用）
  3. 修改Buffer Pool中的数据：在内存中修改数据页（标记为脏页）
  4. 写Redo Log Buffer：记录修改日志到redo log buffer（WAL原则）
  5. COMMIT时：将Redo Log刷盘（fsync），事务标记为已提交
  6. 后台落盘：Checkpoint时脏页异步写入磁盘
图：事务执行的生命周期（InnoDB视角）

WAL（Write-Ahead Logging）是持久性的核心技术：修改数据前，先写日志。这样即使数据库崩溃，重启后可通过Redo Log恢复已提交事务。

核心要点：

事务执行链：找到数据→写Undo(回滚备用)→改内存→写Redo(WAL)→COMMIT刷Redo→后台刷数据页。Crash后Redo Log是最后的防线。

实践应用

实践应用

增删改不是"写完就跑"——工作中真正的DML操作模式

场景1：安全的数据修正

-- 1. 开启事务
START TRANSACTION;
-- 2. 确认目标数据
SELECT * FROM orders WHERE order_no = 'ORD-2026001';
-- 3. 执行修改
UPDATE orders SET amount = 299.99 WHERE order_no = 'ORD-2026001';
-- 4. 验证结果
SELECT * FROM orders WHERE order_no = 'ORD-2026001';
-- 5. 确认无误后提交
COMMIT;
-- 如发现问题，执行 ROLLBACK;

场景2：大批量数据更新

-- 分批更新，避免锁表和长事务
DELIMITER $$
CREATE PROCEDURE batch_update()
BEGIN
  DECLARE done INT DEFAULT 0;
  WHILE done = 0 DO
    START TRANSACTION;
    UPDATE logs SET archived=1 WHERE created_at<'2024-01-01' AND archived=0 LIMIT 1000;
    IF ROW_COUNT() < 1000 THEN SET done = 1; END IF;
    COMMIT;
    DO SLEEP(0.1); -- 给其他查询留出间隙
  END WHILE;
END$$
核心要点：

生产环境DML的两条铁律：(1) 修改前加事务→SELECT确认→修改→SELECT验证→COMMIT；(2) 大批量操作必须分批+间隙，避免长时间锁表。

实践案例

实践案例

电商库存扣减：一个涉及INSERT+UPDATE+事务隔离级别的经典并发场景

场景：下单时需要同时扣减库存、创建订单、记录操作日志——三步必须成原子操作。

START TRANSACTION;

-- 1. 悲观锁锁定库存行，防止超卖
SELECT stock FROM inventory WHERE product_id = 101 FOR UPDATE;

-- 2. 检查库存
SELECT IF(stock > 0, 'ok', 'sold_out') INTO @status
FROM inventory WHERE product_id = 101;

-- 3. 库存充足则扣减
IF @status = 'ok' THEN
  UPDATE inventory SET stock = stock - 1 WHERE product_id = 101;
  INSERT INTO orders (user_id, product_id, amount) VALUES (42, 101, 299.99);
  INSERT INTO order_logs (order_id_msg) VALUES (LAST_INSERT_ID(), 'create');
  COMMIT;
  SELECT 'Order success';
ELSE
  ROLLBACK;
  SELECT 'Sold out';
END IF;
图：库存扣减的并发竞争示例（乐观vs悲观锁）

悲观锁 vs 乐观锁：本例用FOR UPDATE（悲观锁），事务期间锁定该行。在高冲突场景下悲观锁最优。乐观锁（版本号法）适合冲突率低的场景——用UPDATE ... SET stock=stock-1, version=version+1 WHERE version=@old_version。

核心要点：

库存扣减是事务的试金石：SELECT FOR UPDATE(悲观测锁)防备超卖，乐观锁(版本号)适合低冲突。关键是在原子性保障和并发吞吐之间找到平衡点。

风险与陷阱

潜在风险

忘了WHERE、忘了COMMIT、锁了全表——DML的代价比查询高千百倍

🔴 致命级

  • UPDATE/DELETE忘记WHERE：全表更新或删除。必须在生产环境开启sql_safe_updates(MySQL)或使用BEGIN+ROLLBACK先验证
  • 长事务未提交：事务持有锁未释放→其他查询阻塞→数据库连接池耗尽→系统瘫痪
  • 死锁：两个事务相互等待对方持有的锁。InnoDB会自动检测并回滚其中一个

🟠 隐匿陷阱

  • MVCC版本链膨胀：长事务不提交→undo log无法清理→查询变慢
  • 自动提交误区：MySQL默认autocommit=ON，每条语句自动提交。多步操作需显式BEGIN
核心要点：

生产DML三大防线：开启sql_safe_updates防全表操作、超时监控长事务、外键设计防孤儿数据。没有防线的DML就像不带刹车开跑车。

常见问题

常见问题诊断

问题1：UPDATE几万行就锁表了？

分两种情况：索引列上有索引（行锁），无索引（全表锁）。解决：确保UPDATE的WHERE列有索引；分批（LIMIT 1000）操作。

问题2：事务不提交，连接越来越多

查：SHOW PROCESSLIST 或 SELECT * FROM information_schema.INNODB_TRX。杀：KILL QUERY [connection_id]。预防：设置wait_timeout和事务超时。

问题3：自增ID跳号

INSERT失败或ROLLBACK后自增ID不会回退——这是设计上的选择（保证并发插入的连续性）。如需连续编号，应使用业务规则生成而非依赖自增。

核心要点：

更新锁表→确保WHERE列有索引+分批操作；连接堆积→查INNODB_TRX+杀长事务；自增跳号→预期行为，不是bug。

未来趋势

发展趋势

  • 分布式事务进化：从刚性ACID到柔性Saga，微服务架构推动"最终一致性"成为主流。Seata/DTM等框架让分布式事务代码化。
  • HTAP混合事务：TiDB/Google Spanner/CockroachDB可同时做在线事务(OLTP)和实时分析(OLAP)，消除"事务库→数据仓库"的ETL延迟。
  • AI辅助的事务调优：通过机器学习分析查询模式，自动推荐最优隔离级别和锁策略。
核心要点：

事务的未来是"分布式化+柔性化"——传统ACID保留在单库，跨服务走Saga，HTAP打破事务与分析的分界。理解Saga模式是微服务架构师的必备技能。

学习指导

学习建议

  1. 先在开发库练习DML：永远不要在生产环境做第一次DML尝试。准备一个结构和生产一致的测试库
  2. 用EXPLAIN理解UPDATE/DELETE的执行计划：确保WHERE条件走索引
  3. 模拟并发：开两个终端，同时在同一个表上执行UPDATE/INSERT，观察锁等待和死锁
  4. 阅读Redo Log和Undo Log的配置：理解innodb_log_file_size和innodb_undo_tablespaces的含义
核心要点：

DML+事务的学习是"实践驱动型"——在开发库构建真实场景，模拟并发和异常。理论和文档只有在踩过坑后才能真正吸收。

认知纠偏

常见误区

  • "MyISAM比InnoDB快，所以读多写少的表用MyISAM"：已经过时。MySQL 8.0中InnoDB是所有场景的默认引擎，MyISAM不支持事务且已逐步淘汰。
  • "事务隔离级别越高越好"：SERIALIZABLE虽然最安全，但并发性能极差。READ COMMITTED可满足90%的业务需求。
  • "用了事务就不用担心数据丢失"：事务保证ACID的前提是正确配置了Redo Log的fsync策略。innodb_flush_log_at_trx_commit=0会导致崩溃丢数据。
  • "DELETE比TRUNCATE安全"：DELETE可带WHERE和回滚，但大量删除时TRUNCATE(不可回滚)远快于DELETE且不产生undo日志。
核心要点：

InnoDB是唯一选择，READ COMMITTED是默认配置，Redo Log的fsync决定持久性。事务不万能——配置和用法同样重要。

观点碰撞

争议与讨论

强一致性ACID vs 最终一致性BASE——数据库世界的"左右互搏"

ACID阵营：主张事务必须保持强一致性，任何数据变更都应在一个原子边界内完成。银行、支付、库存等核心交易系统必须走这条路。

BASE阵营：认为在网络分区和分布式环境下，追求强一致性代价太高。主张"基本可用+软状态+最终一致"——典型如电商的下单确认(异步短信和实际扣款分开)。

业界实践：核心交易链路走ACID（单库事务），非关键流程走BASE（异步+重试+补偿）。"不追求非必要的一致性"是分布式系统设计的第一原则。

核心要点：

ACID vs BASE不是非此即彼：资金交易用ACID，用户通知用BASE。关键是根据业务影响来选择一致性模型，而非技术偏好。
