基础背景

背景与缘起

数据库的核心价值不在于存储细节，而在于把100万行订单表压缩成一行"上月总销售额：5.38亿"——这就是聚合的力量。

关系代数的五个基本操作中，聚合（Aggregation）常被表示为γ（Gamma）符号。与投影（选列）和选择（筛行）不同，聚合改变了数据的粒度——从逐条记录变为分组统计量。在商业智能和数据分析领域，聚合是绝对核心：财务报表、运营看板、质量监控——所有"从数据中提取洞察"的工作，本质上都是聚合。

SQL定义了五大聚合函数（COUNT/SUM/AVG/MAX/MIN），加上GROUP BY组成数据分析的"瑞士军刀"。而HAVING让聚合结果可被二次过滤，形成了WHERE（行过滤）→ 聚合 → HAVING（组过滤）的完整分析流水线。这套机制自SQL-92以来就是数据分析的基石，至今无可替代。

核心要点：

聚合的本质是数据粒度的跃迁——从明细到汇总。COUNT(*)数总数、SUM算合计、AVG求平均、MAX/MIN找极值。五大函数+GROUP BY+HAVING构成了数据分析的最小完备工具集。

核心概念

核心概念

你知道COUNT(*)和COUNT(column)的区别吗？知道SUM在空集上返回NULL而不是0吗？这些细节决定报表数据是否准确。

五大聚合函数的精确行为

函数作用忽略NULL?空集返回工作场景
COUNT(*)统计所有行否0总行数、分页总数
COUNT(col)统计非NULL值是0有效值计数
SUM(col)求和是NULL总销售额
AVG(col)平均值=SUM/COUNT是NULL平均价格
MAX/MIN(col)最大/最小值是NULL极值查找
AVG的底层计算
$$\text{AVG}(col) = \frac{\text{SUM}(col)}{\text{COUNT}(col)}$$
推导：AVG=SUM/COUNT(col)。注意COUNT(col)会跳NULL，所以分子和分母基于同样的非NULL集合。这意味着如果你手动SUM/COUNT(*)做平均，当列有NULL时结果会偏小。

GROUP BY规则

-- ✅ SELECT中非聚合列必须在GROUP BY中
SELECT department, AVG(salary)
FROM employees GROUP BY department;

-- ❌ job_level没在GROUP BY中——报错
SELECT department, job_level, AVG(salary)
FROM employees GROUP BY department;

HAVING vs WHERE

-- WHERE过滤行（聚合前）→ HAVING过滤组（聚合后）
SELECT department, COUNT(*) AS cnt
FROM employees
WHERE join_date >= '2024-01-01'   -- 先过滤行
GROUP BY department                 -- 再分组
HAVING COUNT(*) > 5                -- 再过滤组
ORDER BY cnt DESC;
核心要点：

COUNT(*)数所有行，COUNT(列)跳NULL；SUM/AVG/MAX/MIN空集返回NULL要用COALESCE兜底；GROUP BY后SELECT中非聚合列必须出现在GROUP BY中。HAVING在聚合后、WHERE在聚合前。

核心原理

核心原理

当数据库执行GROUP BY时，它内部在运行着一个微型的MapReduce——哈希表vs排序，两种策略决定性能。

策略一：哈希聚合（Hash Aggregation）

  1. 遍历WHERE过滤后的结果集，对GROUP BY列计算哈希值
  2. 在内存哈希表中查找/创建分组桶
  3. 更新桶内聚合状态（COUNT+1, SUM累加等）
  4. 遍历完成，所有分组结果已在内存中——直接输出

策略二：排序聚合（Sort Aggregation）

  1. 先按GROUP BY列排序（可能用索引，也可能filesort）
  2. 排序后同组行排在一起
  3. 顺序扫描：发现分组列值变了→输出上一组→开始新分组
时间复杂度对比
$$T_{\text{hash}} \approx O(n), \quad T_{\text{sort}} \approx O(n \log n)$$
决策因素：哈希聚合通常更快，但前提是哈希表能放入work_mem/sort_buffer_size。如果GROUP BY列基数极高（百万组），哈希表可能撑爆内存。优化器会自动选择。
图：Hash Agg vs Sort Agg 执行耗时对比
核心要点：

GROUP BY的两种内部策略：内存够用选Hash（O(n)），有索引选Sort。在高基数（百万分组）场景下，两种策略都可能耗尽内存导致溢出到磁盘。

ROLLUP和CUBE：多维分析利器

-- ROLLUP: 逐级汇总（部门→部门+职级→总计）
SELECT dept, job_level, SUM(salary)
FROM employees GROUP BY ROLLUP(dept, job_level);
-- 输出：IT/senior、IT总计、全公司总计

-- CUBE: 所有维度组合的交叉汇总
SELECT dept, job_level, SUM(salary)
FROM employees GROUP BY CUBE(dept, job_level);
-- 输出：所有维度排列组合 + 各级总计
核心要点：

SQL:1999带来的窗口函数和ROLLUP是多维数据分析的里程碑转折。CUBE和GROUPING SETS让"数据立方体"成为现实——一张报表覆盖所有维度组合。

实践技巧

实践应用

日报、周报、月报——这些每个人逃不掉的汇报，背后都是聚合查询在默默计算。

模式一：单维度汇总

SELECT channel, COUNT(DISTINCT user_id) AS uv,
       COUNT(*) AS pv
FROM page_visits WHERE visit_date=CURDATE()
GROUP BY channel ORDER BY uv DESC;

模式二：多维度交叉分析

SELECT DATE(order_date) AS day, product_category,
       COUNT(*) AS cnt, SUM(amount) AS revenue
FROM orders WHERE order_date>=DATE_SUB(CURDATE(),INTERVAL 30 DAY)
GROUP BY day, product_category ORDER BY day DESC;

模式三：占比分析

SELECT product_category, SUM(amount) AS revenue,
       ROUND(SUM(amount)*100.0/SUM(SUM(amount)) OVER(),2) AS pct
FROM orders GROUP BY product_category ORDER BY revenue DESC;

模式四：同比/环比

SELECT DATE_FORMAT(order_date,'%Y-%m') AS mon,
       SUM(amount) AS revenue,
       LAG(SUM(amount)) OVER(ORDER BY DATE_FORMAT(order_date,'%Y-%m')) AS prev
FROM orders GROUP BY mon ORDER BY mon;
核心要点：

四个模式组合起来就是数据分析的标准流水线：先单维度了解概况→再多维度找关联→算占比看权重→趋势对比判断方向。这是数据分析师每天都在做的事。

实践案例

实践案例

用5个聚合查询，10分钟验证"SaaS活跃用户在增长"这个运营声称是否真实。

-- 查询1: 本周DAU（日活跃用户）
SELECT DATE(action_time) AS day,
       COUNT(DISTINCT user_id) AS dau
FROM user_actions
WHERE action_time>=DATE_SUB(CURDATE(),INTERVAL 7 DAY)
GROUP BY day ORDER BY day;

-- 查询2: 用户活跃天数分布（深度用户 vs 轻度用户）
SELECT days_active, COUNT(*) AS user_cnt
FROM (
  SELECT user_id, COUNT(DISTINCT DATE(action_time)) AS days_active
  FROM user_actions
  WHERE action_time>=DATE_SUB(CURDATE(),INTERVAL 7 DAY)
  GROUP BY user_id
) t GROUP BY days_active ORDER BY days_active DESC;
图：本周DAU趋势与用户活跃度分布

分析结论：DAU本周波动于8500-9300，未显著增长；仅15%用户7天全勤，62%只1-2天活跃——用户留存策略需要优化。运营听到的不是好消息，但是真话。

核心要点：

聚合分析的核心价值是用数据说话。COUNT(DISTINCT)+GROUP BY可以让你在10分钟内拆穿或验证任何"经验判断"。不要让直觉凌驾于数据之上。

风险警示

潜在风险

当GROUP BY吞噬你的数据库内存——高基数分组可能导致OOM崩溃。

风险触发条件后果解决
哈希溢出GROUP BY键基数极高OOM或磁盘溢出增大work_mem+缩小WHERE
AVG精度丢失对FLOAT大表AVG浮点误差，金额差几分钱财务用DECIMAL
COUNT(DISTINCT)低效COUNT(DISTINCT a,b)需额外排序去重用子查询GROUP BY再COUNT

COUNT(DISTINCT)优化

-- ❌ 慢：大表上COUNT(DISTINCT两个列)
SELECT COUNT(DISTINCT user_id, product_id) FROM orders;

-- ✅ 快：先GROUP BY去重再COUNT(*)
SELECT COUNT(*) FROM (
  SELECT 1 FROM orders GROUP BY user_id, product_id
) t;
核心要点：

聚合不是免费的——Hash Agg的内存消耗与GROUP BY基数成正比；财务计算用DECIMAL而非FLOAT；COUNT(DISTINCT多列)可用子查询优化。EXPLAIN是排查聚合性能的唯一工具。

生态格局

OLTP vs OLAP

同一个AVG函数，在行存MySQL和列存ClickHouse中的执行效率可能差100倍。

图：1亿行数据聚合耗时对比（对数尺度）
场景OLTP（行存）OLAP（列存）
典型聚合耗时秒到分钟毫秒到秒
为什么快/慢读整行数据（IO密集）只读需要的列（IO高效）
代表产品MySQL, PostgreSQLClickHouse, DuckDB

如果你的工作涉及大量"全表扫描+多维度聚合"的分析型查询，考虑ClickHouse或DuckDB作为分析引擎——不要在MySQL里死磕OLAP。

核心要点：

行存适合点查和事务，列存适合聚合扫描。100x的性能差异意味着：用错引擎可能需要等5分钟 vs 等3秒。必要时引入DuckDB作为离线分析加速层。

常见陷阱

常见问题

先JOIN再GROUP BY vs 先GROUP BY再JOIN——同样是正确结果，性能可能天差地别。

提前聚合：大数据量的黄金法则

-- ❌ 慢：百万行JOIN后再聚合
SELECT d.name, SUM(o.amount)
FROM orders o
JOIN departments d ON o.dept_id=d.id
GROUP BY d.name;

-- ✅ 快：子查询中先聚合到几十行，再JOIN
SELECT d.name, agg.total
FROM (
  SELECT dept_id, SUM(amount) AS total
  FROM orders GROUP BY dept_id
) agg
JOIN departments d ON agg.dept_id=d.id;

第一种生成百万行JOIN结果再聚合；第二种先将orders缩编为几十行部门汇总。数据量缩小了几个数量级——这就是提前聚合的力量。

核心要点：

先聚合再JOIN是处理关联+分组查询的铁律。把最重的计算压在最小的数据量上——子查询里的GROUP BY能将百万行压缩到几十行。

发展趋势

发展趋势

传统聚合要等T+1入库才能算。流式SQL引擎让聚合在数据产生的那一刻就开始计算。

流式聚合（Streaming Aggregation）是当前数据工程最火的方向。Flink SQL用状态后端维护聚合中间结果，支持Exactly-Once语义——你可以写一条SQL实时计算"过去5分钟每个商品销量TOP 100"，秒级更新排行榜。

趋势：未来2-3年，RisingWave和Materialize等流式数据库成熟后，"流批一体"的聚合SQL将成为数据团队标配。同样的GROUP BY语法，可以在批和流模式间无缝切换。学习聚合永远是保值的——无论底层变成什么，聚合的语法和思维模式不变。

核心要点：

流式聚合正在重塑数据管道的时效性——从T+1到秒级。Flink SQL的GROUP BY和MySQL的GROUP BY语法几乎一样——学会传统聚合，流式聚合只是换了一个运行环境。

学习建议

学习建议

从"知道COUNT怎么写"到"看到查询就知道要建什么索引"——这条路上每一步都有明确的检验标准。

层级技能验证
Level15个聚合函数+GROUP BY/HAVINGLeetCode SQL Medium 10题
Level2聚合与索引关系，EXPLAIN分析10万行聚合优化到<100ms
Level3设计预聚合表/物化视图报表查询从5分钟→2秒

Level 3实战：预聚合表

-- 每天凌晨2点，把前一天订单汇总到daily_order_summary
INSERT INTO daily_order_summary (summary_date,dept_id,order_cnt,revenue)
SELECT DATE(order_date), dept_id, COUNT(*), SUM(amount)
FROM orders WHERE DATE(order_date)=CURDATE()-INTERVAL 1 DAY
GROUP BY DATE(order_date), dept_id;
-- 报表查询直接读汇总表，毫秒级响应
核心要点：

Level1是语法关（正确写出GROUP BY），Level2是性能关（理解Hash/Sort Agg），Level3是架构关（设计预聚合方案）。Level3才是真正的价值——把查询速度从分钟级降到毫秒级。

误区纠正

常见误区

#误区真相
1"COUNT(*)比COUNT(col)慢"InnoDB中COUNT(*)优化为取最小索引计数，通常更快
2"AVG空集应该返回0"SQL中AVG对空集返回NULL——用COALESCE兜底
3"HAVING和WHERE随便互换"WHERE过滤行（聚合前），HAVING过滤组（聚合后）——性能差异巨大
4"GROUP BY自动排序"SQL标准不保证，MySQL旧版本有这行为。要排序显式写ORDER BY
5"SUM(DISTINCT col)等同于正确的去重聚合"如果col有重复值但其他列不同，SUM(DISTINCT)会丢掉有效数据
核心要点：

五个误区中，WHERE/HAVING混淆和GROUP BY自动排序的误解是最隐蔽的——SQL不报错但结果可能是错的。COUNT(*)在InnoDB中是最优的计数方式，不要怕用它。

行业讨论

争议与讨论

聚合到底该在哪一层做？SQL引擎 vs Spark/Flink vs 物化视图——三大阵营各有理由。

阵营策略优点缺点
SQL原教旨一切在数据库里聚合语法简洁、近源OLTP库不适合大聚合
分布式引擎派Spark/Flink数据管道聚合水平扩展、吞吐高运维复杂、SQL兼容差
物化视图派预计算聚合存储查询极快、透明加速数据新鲜度延迟

业界共识：三条腿走路——实时看板用流式聚合（Flink），离线报表用Spark聚合后入数仓，高频小查询用物化视图加速。三个场景三种方案，不互相排斥。

核心要点：

聚合架构没有银弹。实时用Flink、批量用Spark、缓存用物化视图——根据数据新鲜度要求和查询延迟预算选择策略。关键是不要让OLTP库扛分析型聚合。
